該回收的，
被誰一直抓著

記憶體用量一直漲不會降，通常是有東西「該被 GC 回收卻被某個 reference 一直抓著」。要靠 heap snapshot 比對找出兇手。

DEMO — 洩漏 vs 正常 cache

第一步：分辨是真洩漏還是正常

切換看記憶體曲線。重點：洩漏是「無限漲」，正常 cache 是「漲到一個量就穩定」：

切換情境，看曲線
排查步驟

取兩個 snapshot 比對

1

先確認真的是洩漏

看記憶體是「無限漲」還是「漲到一個量就穩定」。

2

取兩個 heap snapshot

壓力測試前 vs 後。

3

用 Comparison view 比對

找「之間新增了一堆、卻沒被釋放」的物件。

4

看 retainer（誰在抓著它）

往上找到 root cause。

工具：--inspect + Chrome DevTools、clinic.js、process.memoryUsage()、Prometheus 監控 nodejs_heap_size_used_bytes。

常見洩漏源

兇手清單

  • 全域 cache 沒設 TTL / 大小上限 → 無限長大。
  • Event listener 加了沒移除（如重複 server.on('connection', ...)）。
  • Closure 抓著大物件 不放。
  • Timer 沒 clear（setInterval 會一直持有 callback reference）。
  • ORM 的 connection / cursor 用完沒關。

30 秒版本

「我會先分辨是真洩漏還是正常 cache（看記憶體會不會穩定下來）。確認後取壓測前後兩個 heap snapshot，用 DevTools 的 comparison view 找新增又沒釋放的物件，再順著 retainer 找 root cause。最常見的兇手是沒清的 event listener、沒設上限的全域 cache、沒 clear 的 timer、和抓著大物件的 closure。」
