網路協定 · 瀏覽器

瀏覽器擋的，
不是 server

瀏覽器預設禁止網頁向「不同來源」的 server 要資料（同源政策）。CORS 是 server 用回應 header 主動「授權」放行的機制。

重點：CORS 是瀏覽器在擋，不是 server。用 curl、Postman 打同一支 API 完全不受影響。它保護的是「使用者的瀏覽器不被惡意網站利用」。
什麼時候觸發 preflight

踩到任一條就要預檢

Simple（直接送）GET/HEAD/POST + 簡單 header + 三種 Content-Type
Preflight（先 OPTIONS）PUT/DELETE/PATCH
Preflight自訂 header 如 Authorization
PreflightContent-Type: application/json ← 99% JSON API

Preflight 流程：瀏覽器先送 OPTIONS 帶 Access-Control-Request-* → server 回 Access-Control-Allow-* + Max-Age（預檢結果可 cache 多久）→ 通過才送真正的請求。

兩個常見地雷

⚠️

Client 要 fetch(url, { credentials: 'include' })；Server 要回 Access-Control-Allow-Credentials: true，而且 Allow-Origin 不能是 *，必須是具體網域。

延伸追問 & 踩雷

常見出事點

為什麼要 preflight 不直接送？

保護那些「沒準備好處理跨源」的舊 server，避免它們收到非預期的 PUT/DELETE 就誤執行。

✕

某個 middleware 把 OPTIONS 攔下來（如 auth 要求 token，但 OPTIONS 不帶 token）→ 預檢失敗。所以 cors 要放在 auth 前面。

✕

Allow-Headers 漏了 Authorization → 帶 token 的請求被擋。

面試這樣答

30 秒版本

「CORS 是瀏覽器同源政策的放行機制，由 server 用 Access-Control-Allow-* header 授權，擋的是瀏覽器不是 server。GET/POST 的簡單請求直接送；但用了 PUT/DELETE、自訂 header、或 Content-Type: application/json（幾乎所有 API）就會先送 OPTIONS 預檢。帶 cookie 時 Allow-Credentials 要 true 且 Allow-Origin 不能用萬用字元。」
