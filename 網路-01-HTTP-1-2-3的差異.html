同一個塞車問題

HTTP 三代演進的核心，都在解決「同一條連線上多個請求互相塞車」（隊頭阻塞）。HTTP/3 甚至為此換掉了底層的 TCP。

核心：隊頭阻塞

Head-of-Line Blocking

  • HTTP/1.1：只有一個收費道，前面那台卡住，後面全等。
  • HTTP/2：開多個收費道（多 stream 並行），應用層不卡了。但底層還是 TCP，要求「封包按順序到」—— 只要一個封包掉了，TCP 讓整條連線停下來等重傳（TCP 層隊頭阻塞），開幾個 stream 都沒用。
  • HTTP/3：改用 QUIC（建在 UDP 上），每個 stream 獨立，一個掉包不影響其他 stream。
為什麼走 UDP & 行動加分點

connection migration

  • TCP 的行為寫死在作業系統核心（kernel），改不動。
  • UDP 在使用者態，QUIC 才能自由設計擁塞控制與多工。
📱

HTTP/3 有 connection migration —— 從 Wi-Fi 切到 4G 時不用重新握手，連線無縫接續。對行動 App 特別有價值。

我的 API 該升 HTTP/3 嗎？

靜態資源（走 CDN）升級 CP 值高；API 看 client 是不是大量行動端。

QUIC 真的比較省？

連線建立省一個 RTT，但 CPU 比 TCP 重（kernel 沒幫忙處理）。

面試這樣答

30 秒版本

「三代主軸都在解決隊頭阻塞。HTTP/1.1 一條連線排隊；HTTP/2 在應用層多工，但底層 TCP 一掉包整條停等；HTTP/3 改用 QUIC over UDP，每個 stream 獨立、掉包互不影響，還內建 TLS 1.3、握手更快、支援連線遷移。要走 UDP 是因為 TCP 寫死在 kernel 改不動。」
