改 API，但別弄壞舊 App

API 上線後一定會改，但已經串接的舊 client 不能說壞就壞。版本控管就是讓 /v1 維持舊行為、新規格放 /v2，舊 client 慢慢遷移，等沒人用了再下線。

沒版本控管：新版一蓋上去，舊 App 立刻崩（用戶又不會馬上更新）。
有版本控管：新格式放 /v2，舊 App 的 /v1 原封不動，零災情。
三種做法

怎麼放版本號

做法範例結論
URL 版本
最常見		/v1/bikes直觀、好 debug、CDN 友善。約 90% 團隊用這個。
Header 版本Accept: …vnd.moovo.v2+jsonURL 不變較「純」，但難測試、cache 複雜。
Query 參數/bikes?version=2cache 行為混亂，不建議。
✅

實務結論：「簡單好維護」遠比「理論純粹」重要，所以多數選 URL 版本。

延伸追問

面試官可能再追

v1 何時能下線？

統計用量 + 給通知期（通常 6 個月）+ 在 response 加 Deprecation / Sunset header 提醒。

怎麼做向後相容？

加欄位 OK；改欄位語意不 OK；要刪欄位先標 deprecate 再刪。

✕

最大的雷：在同一個版本內偷改欄位語意（例如把 status 從數字改成字串）—— 等於暗中破壞相容性。

面試這樣答

30 秒版本

「我會用 URL versioning（/v1），因為直觀、CDN cache 友善、debug 方便。雖然 header versioning 理論上更符合 REST『一個資源一個 URI』，但實務上難測難 cache，多數團隊還是選 URL。下線舊版前會給遷移期並加 Deprecation / Sunset header。」
