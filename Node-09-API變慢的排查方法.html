從 100ms 暴增到 5s，
怎麼查？

這題在測你有沒有「系統化 debug」能力，而不是亂猜。核心心法：分層排查，從外到內，一層層縮小範圍。

常見元兇

最後通常是這幾個

  • 某張表的 index 失效（VACUUM 後、或新欄位排序沒 index）→ 變全表掃描。
  • 連線池耗盡（connection pool exhaustion）→ 請求排隊等連線。
  • 某段同步程式碼意外卡住 Event Loop（JSON.parse 巨大物件、bcrypt 沒用 async 版）。
  • 第三方 API（Stripe）變慢，拖累整條請求。
為什麼要分 P50 / P99

平均值會騙人

P50 高大家普遍變慢 → 系統性問題
只有 P99 高多數正常、少數很慢 → 特定大資料 / 用戶 / GC / 鎖等待
⚠️

只看「平均值」會被極端值帶歪，看不出真相。

面試這樣答

30 秒版本

「我會分層、從外到內：先看 CDN/LB 是不是特定 region，再看是哪個 endpoint、是 P50 還是 P99 高，然後用 APM trace 定位慢在 Node、DB 還是外部 API。DB 慢就 pg_stat_statements + EXPLAIN ANALYZE；懷疑 Node 就看 event loop utilization。常見兇手是 index 失效、連線池耗盡、同步程式卡住 event loop、第三方 API 拖累。如果沒有 APM/log，我會老實說第一步是先補上 observability，否則只能猜。」
