REACT CONTEXT

Context 不是免費的：任何變動都讓所有 consumer 重渲

Context 很方便，但被頻繁更新的值放進去，會讓所有使用 useContext 的組件全部重新渲染，即使它們只用到 Context 裡的一小部分。用前先評估是否合適。

核心問題

Context 值一變，所有 consumer 都重渲

// 每次 ParentComponent 的 count 變，ChildA 也重渲
// 即使 ChildA 只用到 user，跟 count 無關
const ctx = { user, count };
<MyContext.Provider value={ctx}>
  <ChildA />  // useContext(MyContext) → 用到 user
  <ChildB />  // useContext(MyContext) → 用到 count
</MyContext.Provider>
三種緩解策略

如何減少不必要的重渲

拆分 Context：把 UserContext 和 CountContext 分開，各自 consume 各自關心的。
useMemo 記憶 Context 值：const value = useMemo(() => ({ state, dispatch }), [state])，避免物件引用每次重建。
use-context-selector：第三方函式庫，讓你只訂閱 Context 的某個欄位，類似 Redux 的 selector。
⚠️

Context 最適合頻率低的全域資料，如主題（theme）、語系（locale）、登入狀態。頻繁變動的資料（如表單輸入、游標位置）應考慮 Zustand、Jotai 等外部工具。

延伸追問

面試官可能再追

Context.Provider 的 value 用物件時為何每次都重渲？

每次渲染 Provider 的父組件時，value={{ user, count }} 都建立新的物件引用，即使值相同。React 比較的是引用相等性（===），所以每次都判定「值改變了」。解法：用 useMemo。

什麼時候應該放棄 Context，改用 Redux 或 Zustand？

當 Context 的更新頻率高（如即時狀態）、需要 selector 細粒度訂閱、或需要 middleware（logger、thunk）時，外部狀態管理工具更合適。

面試這樣答

30 秒版本

「Context 的主要陷阱是值改變時所有 consumer 全部重渲，即使組件只用到其中一小部分。緩解方式有：拆分 Context（按更新頻率分開）、用 useMemo 記憶 Provider 的 value 物件、或引入 use-context-selector。Context 最適合低頻全域資料（主題、登入狀態），頻繁更新的資料要考慮 Zustand 等外部工具。」
