REACT 架構

Flux：強制單向資料流，讓狀態變更可追蹤

傳統 MVC 的雙向資料流讓大型應用難以除錯。Meta 提出的 Flux 模式強制資料只能沿著 Action → Dispatcher → Store → View 一個方向流動，讓狀態變更可預測、可重現。它也是 Redux 的前身。

四個角色

Flux 的組成與資料流

View（React 組件）：使用者操作觸發 Action
Action：描述「發生什麼事」的資訊載荷 { type, payload }
Dispatcher：中央樞紐，把 Action 廣播給所有 Store
Store：保存應用狀態和業務邏輯，更新後通知 View 重渲
Flux vs Redux

Redux 對 Flux 的演進

面向FluxRedux
Store 數量多個（每個功能各一個）單一全域 store
Dispatcher需要無（reducer 直接處理）

ℹ️

Flux 現在較少直接使用，但它的單向資料流概念影響了 Redux、Vuex、MobX 等現代狀態管理工具的設計。了解 Flux 有助於理解 Redux 的設計哲學。

延伸追問

面試官可能再追

為什麼 Flux 用單向資料流而不是雙向？

雙向資料流（如 Angular 1 的 two-way binding）在大型應用中，一個狀態變化可能連鎖觸發多個更新，難以追蹤根源。單向流讓每次狀態變化的路徑固定且可追溯。

React 的 useReducer 和 Flux/Redux 的關係是什麼？

useReducer 把 Flux/Redux 的模式內建到 React 組件層級——dispatch(action) → reducer → newState。搭配 Context 可以模擬輕量版 Redux，但沒有 middleware 和 DevTools。

面試這樣答

30 秒版本

「Flux 是 Meta 提出的單向資料流架構：View 觸發 Action，Action 透過 Dispatcher 分發給 Store，Store 更新後通知 View 重渲。核心優點是狀態變更路徑固定、可追蹤，解決了雙向資料流難以除錯的問題。Redux 繼承了 Flux 的單向流概念，但簡化為單一 Store + 純函式 reducer，並加上 DevTools 支援時間旅行除錯。」
