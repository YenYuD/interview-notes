REACT 狀態管理

從 Local State 到 Redux：三個問題決定你該用什麼

狀態管理沒有萬用答案，關鍵是問三個問題：這個狀態只有幾個組件需要嗎？更新頻率高嗎？需要中間件或 devtools 嗎？ 答案決定用 State、Context 還是外部工具。

決策矩陣

三種選擇的適用場景

選擇適用情境不適合
useState / useReducer單一組件或幾個相鄰組件的本地狀態；表單、UI 開關、計數器多個遠距組件需要同步
Context跨多層傳遞但不常變動的全域資料；主題、語言、登入使用者高頻更新（每次都觸發所有 consumer）
Redux / Zustand / Jotai大型應用、複雜狀態邏輯、需要 devtools、跨頁面狀態小型應用（overkill）
決策流程

問自己三個問題

這個狀態只屬於當前組件或其直接子組件？ → 用 useState / useReducer，保持本地
需要多層傳遞且更新不頻繁？ → 用 Context，搭配 useMemo 優化 value
狀態複雜、高頻更新、需要中間件或 time-travel debug？ → 用外部狀態管理工具（Redux Toolkit、Zustand）
✅

現代輕量選擇：Zustand 設定極簡、Jotai 以 atom 為單位做細粒度訂閱，比 Redux 輕量許多，適合中型應用取代 Context 高頻更新的問題。

常見誤用

避免這些反模式

Context 高頻更新 把計數器、表單輸入等高頻狀態放進 Context，導致所有 consumer 每次擊鍵都重渲
過早引入 Redux 小型應用就引入 Redux，徒增 boilerplate 和複雜度，useState 完全夠用
延伸追問

面試官可能再追

Context 和 Redux 的核心差異是什麼？

Context 是 React 內建的跨層傳值機制，無快取、無 devtools、任何 value 變更都重渲所有 consumer。Redux 是獨立狀態容器，有 devtools、時間旅行、中間件（非同步 action）、selector 細粒度訂閱，適合複雜業務邏輯。Context 是「傳值管道」，Redux 是「狀態管理系統」。

什麼時候考慮 Zustand 而不是 Redux？

Zustand 設定極簡（幾行就能建立 store）、沒有 boilerplate、支援細粒度訂閱、可在 React 樹之外讀寫狀態。若不需要 Redux 的中間件生態（如 redux-saga）或強型別 action，Zustand 是更輕量的選擇。

面試這樣答

30 秒版本

「我用三個問題決定：狀態只屬於當前組件就用 useState / useReducer，本地管理最簡單；需要多層共享但更新不頻繁（主題、語言）就用 Context，但要注意 Context 高頻更新會讓所有 consumer 重渲；狀態複雜、需要中間件、devtools 或 time-travel debug 才引入 Redux Toolkit 或 Zustand。總原則是從最小工具開始，只在真正需要時升級。」
