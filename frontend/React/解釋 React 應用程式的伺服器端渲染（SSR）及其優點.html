REACT 渲染策略

SSR：伺服器先把 HTML 算好，用戶端再接管互動

SSR（Server-side Rendering）在每次請求時於伺服器渲染 React 組件，把完整 HTML 傳給瀏覽器。用戶端接收 HTML 後，React 水合（hydrate）讓頁面變得可互動。好處是更快的首屏顯示與更好的 SEO。

流程

SSR + Hydration 四步驟

瀏覽器發送請求
伺服器執行 React 組件，生成完整 HTML（含資料）
瀏覽器接收 HTML，立即顯示內容（此時還不可互動）
React 水合：附加事件處理器，頁面變得可互動
SSR vs CSR

什麼時候選 SSR

面向SSRCSR（純前端）
首屏時間快（伺服器直接回 HTML）慢（需先下載 JS 再渲染）
SEO佳（HTML 完整）差（爬蟲看到空殼）
伺服器負擔每次請求都要算無
TTFB（Time to First Byte）稍慢（伺服器要計算）快
ℹ️

SSR 不等於「任何時候都更好」。對於需要個人化資料、且伺服器有充足運算力的頁面，SSR 是好選擇；純互動的管理後台用 CSR 就夠了。

延伸追問

面試官可能再追

SSR 和 SSG 哪個更好？

取決於內容更新頻率。SSG 速度更快（CDN 直出），但建置後不更新；SSR 每次請求都能拿到最新資料，但有伺服器運算成本。ISR 是折衷方案。

水合不匹配（Hydration Mismatch）是什麼？怎麼解決？

伺服器渲染的 HTML 和客戶端 React 組件產生的 HTML 不同，React 會警告並重新渲染。常見原因：用了 typeof window、Date.now()、Math.random()。解法：確保 SSR 和 CSR 的邏輯完全一致，或用 suppressHydrationWarning（謹慎使用）。

面試這樣答

30 秒版本

「SSR 在每次請求時由伺服器渲染完整 HTML 傳給瀏覽器，使用者立即看到內容（即使 JS 還沒載入）。好處是首屏更快、SEO 更好；代價是伺服器每次請求都要計算。之後 React 在客戶端水合（hydrate），附加事件處理器讓頁面可互動。Next.js 的 getServerSideProps 是典型實作。」
