REACT 陷阱

用 index 當 key：重排時狀態對應到錯的項目

陣列索引看似方便，但清單重排或在前面插入元素時，所有後續節點的 key 都改變，React 誤以為是「不同的元素」——已輸入的文字、選中狀態都會對應到錯的資料。

問題示範

在清單前端插入一項，index key 會出什麼事

index 當 key（出 bug） 原來：Apple(key=0), Banana(key=1)
插入後：New(key=0), Apple(key=1), Banana(key=2)
React 以為 key=0 還是同一個 → 把 New 的 input 內容留給 Apple
id 當 key（正確） Apple(key='a'), Banana(key='b')
插入後：New(key='n'), Apple(key='a'), Banana(key='b')
React 正確識別 → Apple 的 input 跟著 Apple 走
兩種影響

效能問題 + Bug 並存

  • 效能問題：React 以為每個節點都是「新的」，進行不必要的 unmount/remount，而不是移動節點。
  • 狀態錯位 Bug：未受控 input（DOM 存狀態）、focus 位置、CSS 動畫等都跟著位置走，而非跟著資料走。
✅

index 當 key 只在以下情況「安全」：清單是靜態的、不重排、不在中間增刪。但即使這樣，用 id 仍是更好的習慣。

延伸追問

面試官可能再追

如果資料本身沒有唯一 id，怎麼辦？

方案一：後端生成穩定 UUID；方案二：在前端新增資料時用 crypto.randomUUID() 生成並存入 state（不要在 render 函式裡生成，每次渲染都會不同）。

為什麼 React 要用 key 而不是用節點內容比對？

內容比對太昂貴且不精確（相同內容的節點是不同的）。key 讓開發者明確告訴 React「哪個是哪個」，是效能和正確性的最佳平衡。

面試這樣答

30 秒版本

「用陣列索引當 key，在清單重排或在前面插入時，後續節點的 key 全都移位，React 誤以為是不同的元素——導致 DOM 狀態（input 值、focus）對應到錯的資料項，同時也有效能損耗（不必要的 remount）。解法是用資料的穩定唯一 id。只有靜態、不重排的清單才可接受用 index。」
