TYPESCRIPT

型別斷言是你對 TypeScript 說「相信我，我知道型別」

型別斷言讓你覆蓋 TypeScript 的推斷結果，強制指定型別。它只影響編譯期，不在執行期做任何轉換——斷言錯了，runtime 照樣炸。應視為最後手段，優先用 Type Guard。

01

兩種語法

as 語法（推薦）JSX/TSX 也能用
<Type> 語法不能在 JSX 中使用
// 推薦：as 語法
const name = (person.name as string);

// 角括號語法（不能在 .tsx 中使用）
const name = (<string>person.name);
02

常見使用場景

// 1. DOM 操作：querySelector 回傳 Element | null
const input = document.querySelector("#email") as HTMLInputElement;
input.value = "test@example.com"; // ✅ HTMLInputElement 才有 .value

// 2. 非空斷言 ! — 告訴 TS「這不是 null 也不是 undefined」
const el = document.querySelector("#app")!;

// 3. 縮小到更具體的子型別
type Animal = Cat | Dog;
function handleAnimal(a: Animal) {
  const cat = a as Cat; // 你確定這是 Cat
}
⚠️

型別斷言不做執行期檢查。斷言錯誤時，TypeScript 沉默，但 runtime 可能出錯：const user = {} as User; user.name.toUpperCase() → 執行期爆炸。

03

as unknown as T：強制斷言的跳板

const num = 42 as string;           // ❌ 兩個型別沒有重疊
const num = 42 as unknown as string; // ✅ 先斷言到 unknown 再跳
// 這樣做通常代表設計有問題，是最後的逃生口
Type Guard 是更好的替代方案：if (typeof x === "string") { ... }，讓 TypeScript 自動推斷而不是強制覆蓋。
延伸追問

面試官可能再追

型別斷言和型別轉換（Type Cast）的差別？

型別斷言只告訴 TypeScript「這個值的型別是 X」，不產生任何執行期程式碼；型別轉換（如 JavaScript 的 Number("42")）會在執行期真的轉換值。TypeScript 的 as 是純編譯期操作。

什麼時候應該用 Type Guard 代替斷言？

幾乎所有情況都應該優先用 Type Guard（typeof、instanceof、自訂 is 型別守衛），讓 TypeScript 自動推斷而不是強制覆蓋。斷言適合「你確定 TypeScript 推斷不準確且你掌握更多資訊」的情況，如 DOM 存取。

面試這樣答

30 秒版本

「型別斷言（as Type）讓你告訴 TypeScript 某個值的確切型別，覆蓋它的推斷。關鍵是它只影響編譯期，不在執行期做任何轉換或驗證——斷言錯了一樣會在 runtime 出錯。常見用途是 DOM 操作（querySelector 回傳 Element，你知道是 HTMLInputElement）和處理外部資料。斷言應視為最後手段，大多數情況應優先用 Type Guard 讓 TypeScript 自動推斷正確型別。」
