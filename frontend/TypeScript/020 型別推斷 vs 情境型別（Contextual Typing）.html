兩種「不用手寫型別」的反向魔法

型別推斷：值 → 型別（看你給的值）。情境型別：情境 → 型別（看你把函式放在哪）。後者正是為什麼 callback 參數不用手動標型別。

兩者都讓你少寫標注又不失型別安全。理解情境型別，就懂為什麼 React 的 onClick={e => …} 裡 e 自動是 MouseEvent——TS 從 onClick 的定義反推出來了。

延伸追問

面試官可能再追

什麼時候還是該手動標型別？

函式參數（非 callback）、公開 API 邊界、想固定回傳型別當契約時。推斷適合區域變數，邊界處明確標注較安全好讀。

推斷會推出 any 嗎？

會。沒初始值又沒標型別、或關閉 noImplicitAny 時可能落到 any。開啟 strict 能逼你補上。

面試這樣答

30 秒版本

「兩個都是少寫型別的機制。型別推斷是『值 → 型別』，從初始值推出變數型別；情境型別是反向的『情境 → 型別』，從函式被放置的位置推出參數型別——這就是 callback 和事件處理器參數不用手寫型別的原因。區域變數靠推斷，API 邊界我仍會明確標注。」
