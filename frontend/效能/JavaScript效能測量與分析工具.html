前端效能

先量再優化，別憑感覺猜瓶頸

效能問題不靠直覺，靠數據。Chrome DevTools、Lighthouse、WebPageTest 各有定位：從單次剖析到跨地點壓測，選對工具才能找到真正的慢點。

工具全覽

四種工具的定位

工具最強項何時用
Chrome DevTools PerformanceCall stack、重排、JS 執行熱點本地調查單一互動卡頓
LighthouseLCP、TBT、CLS 指標 + 改善建議每次 PR 前跑一次當基線
WebPageTest真實裝置 × 全球節點 × 網路模擬上線前驗收 / 多地點對比
Performance API程式碼內嵌量測、User Timing量測特定函式或流程耗時
關鍵操作

DevTools Performance 三步走

Ctrl+Shift+I → Performance — 打開面板，按「記錄」前先停用快取（Network → Disable cache）。
操作後停止錄製 — 重現問題場景（滾動、點擊、送出表單），再按「停止」。
看火焰圖（Flame chart） — 找長條：主執行緒佔滿 → JS 問題；Layout/Paint 佔多 → DOM 問題。
💡

程式碼內嵌量測用 performance.mark('start') / performance.measure('task','start','end')，比 console.time 更精準，並自動整合進 DevTools Timeline。

實用片段

User Timing API

// 量測一段邏輯的耗時
performance.mark('parse-start');
doHeavyParsing();
performance.mark('parse-end');
performance.measure('parsing', 'parse-start', 'parse-end');

const [entry] = performance.getEntriesByName('parsing');
console.log(entry.duration + ' ms');

面試官可能再追

Lighthouse 分數低，先看哪個指標？

先看 LCP（最大內容繪製）和 TBT（總封鎖時間）——前者影響使用者「感覺快不快」，後者反映主執行緒被佔據程度。CLS 影響視覺穩定性也不能忽略。

production 環境如何持續監控效能？

使用 Real User Monitoring（RUM）方案（如 web-vitals.js + Analytics 或 Sentry Performance），收集真實用戶的 Core Web Vitals，而非只靠 lab data。

Performance.now() 和 Date.now() 差在哪？

performance.now() 回傳高精度浮點毫秒（精準到微秒）且不受系統時鐘調整影響，適合效能量測；Date.now() 回傳整數毫秒且可被 NTP 校正，適合時間戳。

面試這樣答

30 秒版本

「效能優化前我一定先量測。本地調查用 Chrome DevTools Performance 的火焰圖找 JS 熱點和長重排；Lighthouse 跑 Core Web Vitals 當每次上線的基線；WebPageTest 做跨地點、真實網路的壓測。程式碼層面我會用 performance.mark/measure 精確量測特定函式，才不會憑感覺亂優化。」
