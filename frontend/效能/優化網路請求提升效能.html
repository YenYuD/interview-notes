前端效能

請求越少、傳得越小，頁面越快

網路是效能的最大瓶頸之一。減少請求數、壓縮傳輸量、善用快取——這三個方向下手，能讓絕大多數頁面快上一截。

API 優化

資料層的精簡

💡

只取需要的欄位：REST API 常回傳整個物件，前端只用幾個欄位。可改用 GraphQL 按需請求，或後端提供精簡的 BFF（Backend for Frontend）端點。

ℹ️

HTTP/2 多工：同一 TCP 連線可並行傳送多個請求，解決 HTTP/1.1 的 head-of-line blocking，讓小資源不互相等待。

延伸追問

面試官可能再追

Brotli 和 Gzip 怎麼選？

Brotli 壓縮率通常比 Gzip 高 15–25%，但需要 HTTPS。現代瀏覽器都支援，伺服器配置後會根據 Accept-Encoding 標頭自動選擇。新專案優先用 Brotli，Gzip 作為 fallback。

preload 和 prefetch 差在哪？

rel="preload" 提前下載當前頁面即將需要的關鍵資源（高優先度）；rel="prefetch" 低優先度預下載下一頁可能需要的資源，利用瀏覽器空閒時間。

面試這樣答

30 秒版本

「優化網路請求從三個方向下手：減少請求次數——合併資源、延遲載入非必要資源；壓縮傳輸量——Brotli/Gzip 壓縮、minify、圖片用 WebP/AVIF 加 srcset；善用快取——靜態資源加 content hash 配長期 max-age、動態資源用 ETag 驗證。上 CDN 降低延遲、HTTP/2 啟用多工，這幾點組合起來就能明顯改善載入效能。」
