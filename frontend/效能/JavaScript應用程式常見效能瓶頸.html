最常踩的坑

Layout Thrashing

在迴圈裡交錯讀寫 DOM 屬性，瀏覽器每次讀取前都必須先完成排版，效能直接崩潰。

錯誤方式讀寫交錯
正確方式批次讀再批次寫
// ❌ 每次迴圈都強迫同步重排
boxes.forEach(box => {
  const h = box.offsetHeight;   // 讀
  box.style.height = h + 'px';  // 寫 → 強制重排
});

// ✅ 先批次讀，再批次寫
const heights = boxes.map(b => b.offsetHeight); // 全部讀
boxes.forEach((b, i) => b.style.height = heights[i] + 'px'); // 全部寫
記憶體洩漏

最常忘的兩種情形

⚠️

未移除的 event listener：元件卸載後 listener 仍活著，持有元件閉包，GC 無法回收。React 在 useEffect 裡必須 return 清理函式。

ℹ️

循環參考：現代 JS 引擎的 mark-and-sweep GC 可處理大部分循環參考，但若牽涉 DOM + JS 跨環境參考仍可能洩漏。

延伸追問

面試官可能再追

Web Worker 有什麼限制？

無法存取 DOM，與主執行緒透過 postMessage 傳遞資料（值複製或 Transferable）。適合純運算；不適合需要即時操作 UI 的任務。

怎麼偵測記憶體洩漏？

Chrome DevTools → Memory 面板 → 多次拍快照（Heap Snapshot）比較差異；或用 Allocation timeline 觀察持續增長的物件。

面試這樣答

30 秒版本

「JS 應用常見瓶頸有幾類：頻繁 DOM 操作或 layout thrashing 造成卡頓，要批次讀寫；重度運算阻塞主執行緒，用 Web Worker 分擔；記憶體洩漏源自未清除的 listener 或閉包持有。診斷時先用 DevTools Performance 火焰圖確認熱點，再對症處理，避免憑感覺亂優化。」
