CSS / 選擇器

瀏覽器從右到左讀選擇器——這讓短選擇器更快

CSS 選擇器的匹配是從右到左進行的。瀏覽器先找所有符合關鍵選擇器（最右邊）的元素，再向上確認父元素是否也符合。選擇器鏈越短，匹配越快。

核心機制

從右到左：以 p span 為例

瀏覽器讀到選擇器 p span
從關鍵選擇器（最右端 span）出發，在 DOM 中找到所有 <span>
對每個 <span>，向上遍歷父元素，尋找是否有 <p>
找到 <p> 祖先就確認匹配，停止向上遍歷
⚠️

如果關鍵選擇器是 * 或標籤（如 div），瀏覽器需要先篩選大量元素，再逐一向上確認，效能差。

效能建議

讓選擇器更高效

低效（廣泛的關鍵選擇器） div p span、.sidebar ul li a——鏈太長，每個 span/a 都需向上多層確認
高效（單一 class） .nav-link、.article-title——直接命中，無需向上走訪，這是 BEM 的副作用
實際影響：現代瀏覽器的 CSS 引擎已非常快，選擇器效能在大多數頁面中不是瓶頸。但在大型 DOM（數千個節點）或有大量動態更新的場景中仍值得注意。
延伸追問

面試官可能再追

為什麼從右到左而不是從左到右？

從左到右讀 div span 需要先找所有 div，再在每個 div 的後代中找 span，如果頁面有 1000 個 div，就需要遍歷大量子樹。從右到左只需要找所有 span（通常比 div 少），再向上確認是否有 div 父元素，平均需要遍歷的路徑更短。

面試這樣答

30 秒版本

「瀏覽器從最右邊的關鍵選擇器開始，在 DOM 中找到所有符合的元素，再向上遍歷確認父元素是否也符合選擇器。以 p span 為例：先找所有 span，對每個 span 向上找是否有 p 祖先。這就是為什麼關鍵選擇器是通用 * 或標籤名時效能差——匹配到太多元素。最高效的寫法是用單一 class 直接命中，這也是 BEM 方法論帶來的副作用。」
