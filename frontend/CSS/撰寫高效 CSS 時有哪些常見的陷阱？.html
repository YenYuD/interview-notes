CSS / 效能

瀏覽器從右到左讀選擇器——你寫 CSS 的方向反了

CSS 效能問題常見於低效選擇器和觸發重排的屬性。理解瀏覽器如何匹配選擇器、哪些屬性觸發 reflow/repaint，就能寫出更流暢的 CSS。

核心概念一

選擇器：從右到左匹配

瀏覽器從最右邊（關鍵選擇器）開始篩選 DOM，再向上確認父元素是否符合。選擇器鏈越短，瀏覽器工作量越少。

低效：通用/標籤關鍵選擇器 div span、* { ... }——先找所有 span，再逐一往上確認父元素是否為 div
高效：單一 class 關鍵選擇器 .nav-link——直接命中，無需向上走訪
💡

BEM 方法論的副作用就是高效 CSS：所有樣式盡量用單一 class 命中（如 .block__element--modifier），選擇器又短又明確。

核心概念二

避免觸發 Reflow 的屬性

觸發層級代表屬性效能影響
Reflow（重排）width、height、padding、margin、top/left最重：重新計算整個版面
Repaint（重繪）color、background-color、visibility中：重繪像素，不改版面
Composite（合成）transform、opacity最輕：只在 GPU 合成層處理
⚠️

動畫盡量只改 transform 和 opacity，瀏覽器可在 GPU 合成層處理，不觸發 reflow，效能最佳。

延伸追問

面試官可能再追

什麼是強制同步佈局（Forced Synchronous Layout）？

在 JavaScript 中先修改 DOM 樣式，然後馬上讀取 offsetWidth、scrollTop 等佈局屬性，瀏覽器必須立即強制重新計算佈局，而不能等到下一幀批次處理。這會造成效能瓶頸，應盡量批次讀寫或用 requestAnimationFrame 分離讀寫操作。

will-change 屬性有什麼用？

will-change: transform 提前告知瀏覽器這個元素的 transform 即將改變，讓瀏覽器提前建立 GPU 合成層。但不要濫用——過多合成層會消耗大量記憶體，只在確定有效能問題時才針對性使用。

面試這樣答

30 秒版本

「寫高效 CSS 有兩個主要關注點：一是選擇器效率——瀏覽器從右到左匹配，通用選擇器（*）或標籤選擇器作為關鍵選擇器時會匹配大量元素；盡量用單一 class 直接命中。二是避免觸發 reflow——改變 width、height 等版面屬性會讓整個頁面重新計算；動畫盡量只改 transform 和 opacity，瀏覽器在 GPU 合成層處理，效能最佳。」
