JavaScript / 瀏覽器相容

偵測「能不能用」而非「是哪個瀏覽器」——功能偵測才可靠

處理瀏覽器相容有三種方式：直接偵測 API 是否存在（最可靠）、根據某功能的存在推斷其他功能（不可靠）、或解析 UA 字串（最不可靠）。現代開發永遠優先功能偵測。

三種方式比較

可靠度由高到低

功能偵測（Feature Detection）— 最推薦 直接檢查 API 是否存在，根據結果執行不同程式碼： 
if ('geolocation' in navigator) {
  navigator.geolocation.getCurrentPosition(cb);
} else {
  showLocationFallback();
}

/* CSS @supports */
@supports (display: grid) {
  .layout { display: grid; }
}
功能推斷（Feature Inference）— 不推薦 假設「有 A 功能就一定有 B 功能」，這種假設不可靠： 
// ❌ 有 getElementsByTagName 就用 getElementById？
if (document.getElementsByTagName) {
  el = document.getElementById(id); // 邏輯不嚴謹
}
UA 字串（User-Agent String）— 避免 難以解析、可被偽造，Chrome 回報自己同時是 Chrome 和 Safari，可靠性極低。
工具推薦

Modernizr — 功能偵測函式庫

Modernizr 針對數十種 HTML5/CSS3 功能做偵測，並在 <html> 標籤上加 class（如 .flexbox、.no-webgl），讓 CSS 可以根據功能支援情況套用不同樣式。

ℹ️

現代開發中，CSS 的 @supports 可以在不依賴 JS 的情況下做 CSS 功能偵測；JS API 偵測則直接 if ('api' in obj) 即可，Modernizr 的必要性已降低很多。

延伸追問

面試官可能再追

UA 字串的哪些問題讓它不可靠？

1. Chrome 回報自己是 Chrome AND Safari（歷史相容原因），要排除 Safari 需要同時檢查兩個字串。2. UA 字串可以被使用者或工具偽造。3. 各瀏覽器的 UA 字串格式不一致，解析複雜且容易出錯。4. 未來瀏覽器可能改變 UA 字串格式，讓現有的解析邏輯失效。

Modernizr 在現代專案還有用嗎？

需求已大幅減少。CSS @supports 覆蓋了 CSS 功能偵測；JS API 直接 in 運算子或 optional chaining 即可偵測。Modernizr 對需要支援大量舊版瀏覽器且有複雜降級需求的企業專案仍有價值，但現代新專案通常不需要。

面試這樣答

30 秒版本

「三種方式可靠度差很多。功能偵測直接問「這個 API 存在嗎？」，是最可靠的方式，CSS 用 @supports，JS 用 'api' in obj。功能推斷假設有 A 功能就有 B，邏輯不嚴謹，不推薦。UA 字串最不可靠——可被偽造、格式不一致，Chrome 甚至同時回報自己是 Chrome 和 Safari，解析極易出錯，應避免。」
