舊瀏覽器也能跑新 API？Polyfill 就是那塊墊片

Polyfill 是一段「功能偵測 + 替代實作」的 JavaScript，讓你用現代語法卻不放棄舊瀏覽器支援，是相容性策略的核心工具。

核心原理

先偵測、再填補

Polyfill 的邏輯很直接：先檢查瀏覽器是否原生支援，若不支援則注入替代實作，若已支援則什麼都不做（避免覆蓋原生實作）。

// Array.prototype.includes 的 polyfill 範例
if (!Array.prototype.includes) {
  Array.prototype.includes = function(searchElement) {
    for (var i = 0; i < this.length; i++) {
      if (this[i] === searchElement) return true;
    }
    return false;
  };
}
Polyfill vs Transpile：Polyfill 是補 執行時缺少的 API（如 Promise、fetch）；Transpile（Babel）是把新語法（如箭頭函式、可選鏈）轉成舊語法。實務上通常兩者並用。

注意事項

別讓 polyfill 拖垮效能

⚠️

選擇性載入：不要把所有 polyfill 都全量打包。現代瀏覽器根本不需要 polyfill，卻要下載一大包是浪費。用 Polyfill.io 或 @babel/preset-env + useBuiltIns: 'usage' 讓工具自動按需注入。

💡

module/nomodule 技巧：用 <script type="module"> 給現代瀏覽器，<script nomodule> 給舊瀏覽器加載 polyfill 版本——兩者互斥，達到差異化下載。

延伸追問

面試官可能再追

Polyfill 和 Shim 有什麼差別？

兩者常混用，但嚴格來說：Polyfill 是利用當前環境已有的 API，模擬「本應存在但缺失」的原生行為；Shim 泛指任何插入在 API 層與呼叫者之間的適配層，不一定是補缺失功能。實務上 polyfill 是 shim 的子集。

為什麼不能所有東西都 polyfill？

部分平台能力根本無法用 JavaScript 模擬，如 CSS Grid 在舊 IE 的完整支援、Service Worker、WebAssembly 等。這類功能只能用漸進增強（progressive enhancement）策略——有支援就用，沒有就降級到功能性替代方案。

面試這樣答

30 秒版本

「Polyfill 是一段先做功能偵測、若環境不支援就注入替代實作的 JavaScript，讓開發者能使用現代 API 又兼顧舊瀏覽器。例如 IE 11 沒有 Array.prototype.includes，就可以手動或透過 core-js 補上。實務上我通常用 @babel/preset-env 搭配 browserslist，讓工具自動分析並按需注入，避免全量引入拖垮 bundle 大小。」
