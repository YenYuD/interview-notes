函式・非同步

把「接下來要做什麼」當參數傳進去：Callback 回呼函式

回呼函式是作為參數傳入另一個函式，並在某件事完成後被呼叫的函式。它是 JavaScript非同步程式設計的基石，也是理解 Promise / async-await 的前提。

同步 vs 非同步

兩種使用情境

同步回呼：立即執行 
[1, 2, 3].forEach(n => console.log(n));
// 立即依序輸出 1, 2, 3
非同步回呼：等完成再執行 
setTimeout(() => {
  console.log('1 秒後才執行');
}, 1000);
三大應用場景

回呼函式在哪裡出現？

事件處理 — 告訴瀏覽器「使用者點擊時執行這個」 
btn.addEventListener('click', () => doSomething());
計時器 — setTimeout / setInterval 
setInterval(() => updateClock(), 1000);
陣列高階方法 — 把操作邏輯外包 
const evens = [1,2,3,4].filter(n => n % 2 === 0);
⚠️

回呼函式巢狀太深會造成Callback Hell（回呼地獄），程式碼難以維護。現代 JavaScript 用 Promise 和 async/await 解決這個問題。

延伸追問

面試官可能再追

回呼地獄（Callback Hell）是什麼？怎麼解？

多個非同步操作依序串接時，回呼不斷巢狀縮排，形如金字塔，難以閱讀和錯誤處理。解法：Promise 鏈式（.then）或 async/await 扁平化。

回呼和 Promise 的錯誤處理有什麼不同？

傳統回呼慣例用 Node.js 風格 (err, data) 第一個參數傳錯誤，容易被忽略；Promise 用 .catch() 或 try/catch 更統一，且錯誤未處理時有明確警告。

面試這樣答

30 秒版本

「回呼函式是作為參數傳入、在特定時機被呼叫的函式。它是 JavaScript 非同步程式設計的基礎——事件監聽、setTimeout、AJAX 都依賴它。缺點是多層巢狀會形成回呼地獄，可讀性差且難處理錯誤。這也是 Promise 和 async/await 出現的原因。現代程式碼我優先用 async/await，但理解回呼是理解整個非同步模型的基礎。」
