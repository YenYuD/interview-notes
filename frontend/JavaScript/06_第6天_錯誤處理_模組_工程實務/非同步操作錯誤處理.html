非同步錯誤不跑同步的路，catch 位置決定一切

同步程式碼用 try…catch 很直覺，但非同步的錯誤「不在同一個 tick」發生——Promise 的 rejection 與 async/await 的拋出，有各自的捕捉方式。

兩種寫法

async/await vs Promise chain

// ① async/await — 同步感，try…catch 包住
async function loadUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (e) {
    console.error('載入使用者失敗：', e.message);
    return null;
  }
}

// ② Promise chain — .catch() 在鏈末
fetch('/api/users/1')
  .then(res => res.json())
  .then(user => console.log(user))
  .catch(e => console.error('失敗：', e.message));
⚠️

fetch 不會對 4xx/5xx 拋出錯誤！只有網路失敗才 reject。收到 HTTP 錯誤狀態時 res.ok 為 false，需自行 throw。

進階：平行請求的錯誤

Promise.all vs Promise.allSettled

方法有一個 reject 時適用情境
Promise.all 整體立刻 reject，其他 Promise 結果丟棄 全部成功才有意義的請求
Promise.allSettled 等全部完成，每個結果標記 fulfilled/rejected 部分失敗也可繼續的請求 
const results = await Promise.allSettled([
  fetch('/api/a'),
  fetch('/api/b'),
]);
results.forEach(r => {
  if (r.status === 'fulfilled') console.log(r.value);
  else console.error('失敗：', r.reason);
});
延伸追問

面試官可能再追

為什麼不能用同步 try…catch 捕捉普通 Promise 的錯誤？

因為 Promise 的 reject 發生在下一個 microtask（微任務），已離開當前的同步執行上下文。try…catch 只能捕捉同步拋出的錯誤，而 await 關鍵字的作用就是把非同步結果「同步化」，讓 try…catch 得以捕捉。

如何避免每個 async 函式都寫重複的 try…catch？

可以寫一個 wrapper：const [err, data] = await to(promise)（類似 Go 風格）；或在 axios/fetch 封裝層統一處理，只把業務層需要的錯誤向上拋。避免錯誤處理邏輯散落各處。

面試這樣答

30 秒版本

「非同步錯誤處理有兩種主要方式：async/await 搭配 try…catch 讀起來像同步，是我的首選；Promise chain 搭配 .catch() 適合純 Promise 風格。兩個陷阱要注意：第一，fetch 的 HTTP 錯誤不會自動 reject，要自己檢查 res.ok；第二，平行請求用 Promise.allSettled 比 Promise.all 更容錯——後者只要一個失敗就全部丟棄。」
