JavaScript · 錯誤處理

無論如何都要執行的那段程式碼

finally 區塊在 try 與 catch 執行完後必定執行，就算中途 return 也不例外。它是資源清理的最後保障，也是 API 呼叫中「隱藏 loading 狀態」的慣用寫法。

三種情境

finally 為何「必定」執行

1

正常完成：try 執行完

try 無錯誤 → 跳過 catch → 執行 finally。

2

發生錯誤：catch 執行完

try 拋出錯誤 → 執行 catch → 執行 finally。

!

中途 return：finally 仍然執行

即使 try 或 catch 裡寫了 return，函式實際返回前仍會先跑完 finally。

function example() {
  try {
    return 'try 的回傳值';
  } finally {
    console.log('finally 先執行'); // 這行先印
  }
}
console.log(example());
// finally 先執行
// try 的回傳值
實務用途

loading 狀態與資源釋放

async function fetchData() {
  setLoading(true);               // 顯示 spinner
  try {
    const res = await fetch('/api/data');
    return await res.json();
  } catch (e) {
    setError(e.message);
  } finally {
    setLoading(false);            // 無論成功或失敗都隱藏 spinner
  }
}
💡

Promise 的 .finally()：Promise chain 也有對應方法 .finally(() => ...)，語義相同——無論 resolve 或 reject 都執行，且不接收引數、不改變 Promise 的值。

⚠️

陷阱：若 finally 裡也有 return，它會覆蓋 try/catch 的回傳值。這幾乎總是 bug，應避免在 finally 裡寫 return。

延伸追問

面試官可能再追

finally 裡可以 throw 嗎？

可以，但會蓋掉原來的錯誤。如果 try 拋出錯誤 A，finally 又拋出錯誤 B，catch 只會接到 B，原始錯誤 A 被靜默丟棄。這是需要特別小心的行為。

什麼時候不需要 finally，用 .finally() 更好？

當你使用 Promise chain 風格（.then().catch()）時，搭配 .finally() 比混用 async/await 和 try/catch 更一致。兩者功能相同，看整體程式碼風格選擇。

30 秒版本

「finally 區塊的作用是確保某段程式碼無論成功或失敗都一定執行，常用於資源清理與 UI 狀態重設，例如 API 呼叫後關掉 loading 指示器。它有一個重要特性：即使 try 或 catch 裡寫了 return，finally 仍然在函式真正回傳之前執行。Promise 的 .finally() 語義相同，不改變 Promise 的最終值，只保證清理邏輯執行。」
