JavaScript · 記憶體管理

你不 free()，但引擎也不是萬能

JS 有自動垃圾回收（GC），但仍會記憶體洩漏。理解「可達性」與「標記清除」，才能知道哪些程式碼會讓記憶體悄悄吃光。

核心機制

標記清除：GC 的主力演算法

1

標記（Mark）

從根物件（全域變數、執行中的函式參數）出發，遞迴走訪所有可達物件，標記為「存活」。

2

清除（Sweep）

掃描整個堆積（heap），回收所有未被標記的物件所佔記憶體。

✓

可達性 = 活著的判準

只要從根節點有任何參考鏈指向物件，它就不會被回收，無論是否「實際用到」。

世代垃圾回收（Generational GC）：V8 等現代引擎將物件分為年輕代（新建物件，頻繁回收）與老年代（存活久的物件，較少回收），大幅降低 GC 停頓時間。
記憶體洩漏

四種常見的「物件走不掉」情境

原因說明修法
全域變數 意外不加 let/const 宣告，變數掛在 window 嚴格模式 'use strict'
事件監聽器未移除 元件銷毀時未 removeEventListener 在 cleanup 裡明確移除
計時器忘了清 setInterval 的 callback 持有外部參考 clearInterval 在不需要時呼叫
脫離的 DOM 節點 節點從 DOM 移除，JS 變數仍持有其參考 不再需要時將變數設為 null
⚠️

循環參考：舊版 IE 的參考計數演算法會洩漏循環參考，但現代引擎用標記清除已不成問題——因為可達性比參考數更精確。

WeakMap / WeakRef 與 GC 的關係？

WeakMap 的 key 是弱參考，key 物件若無其他強參考，GC 可以回收它，map entry 也會消失。適合快取「以物件為鍵」的資料，不阻止物件被回收。

如何在 Chrome DevTools 偵測記憶體洩漏？

開啟 Memory 面板 → 拍多張 Heap Snapshot → 比較兩次快照的 Objects allocated between snapshots，觀察哪類物件數量持續增加。也可用 Performance 面板觀察 JS Heap Size 是否持續攀升。

面試這樣答

30 秒版本

「JS 的 GC 主要靠標記清除：從根物件開始走訪所有可達物件並標記，接著清除未標記的物件。現代引擎還用世代回收優化效率，讓年輕代頻繁小回收，老年代偶爾大回收。雖然 GC 是自動的，但開發者仍可能造成記憶體洩漏，常見來源是未移除的事件監聽器、忘清的 setInterval，以及對已移出 DOM 節點的持有參考。」
