try…catch 不只是包住錯誤，還要分層處理

try…catch 是 JavaScript 同步錯誤處理的核心語法。關鍵不在會不會寫，而在於「在對的層級 catch」「何時 re-throw」「finally 怎麼用」——這才是面試想測的。

基本結構

三個區塊各自的職責

try {
  // 可能拋出錯誤的程式碼
  const data = JSON.parse(invalidJson);
} catch (error) {
  // 接住錯誤，error 物件有 .name、.message、.stack
  console.error('解析失敗：', error.message);
} finally {
  // 無論是否出錯，都執行（清理資源）
  setLoading(false);
}
try保護區，拋出後立即跳 catch
catch (e)e.name / e.message / e.stack
finally必定執行，適合 cleanup
進階技巧

巢狀 vs 重新拋出

並非所有錯誤都應在同一層處理。兩種進階用法：

巢狀 catch：細粒度錯誤隔離

try {
  const user = await fetchUser();
  try {
    const posts = await fetchPosts(user.id);
  } catch (postsErr) {
    // 貼文失敗不影響使用者資訊的顯示
    console.warn('貼文載入失敗', postsErr.message);
  }
} catch (userErr) {
  // 使用者載入失敗才是嚴重問題
  showError(userErr.message);
}

重新拋出（re-throw）：只處理自己能處理的

try {
  riskyOp();
} catch (e) {
  if (e instanceof NetworkError) {
    retry();         // 處理得了的自己來
  } else {
    throw e;         // 處理不了的往上傳，不要吞掉
  }
}
⚠️

常見錯誤：catch 之後什麼都不做（空 catch block）。這會讓錯誤被靜默吞掉，完全無法除錯。至少要 console.error(e) 或 re-throw。

延伸追問

面試官可能再追

catch 能夠捕捉所有錯誤嗎？

不能。SyntaxError（非執行時）、跨執行緒的 Worker 錯誤、以及未 await 的 rejected Promise 都不會被同步 try…catch 捕捉。非同步錯誤需要 async/await 搭配 try…catch 或 .catch()。

error 物件上有哪些屬性？

標準屬性：name（錯誤類型，如 'TypeError'）、message（可讀說明）、stack（堆疊追蹤字串）。自訂錯誤可擴充更多屬性（如 errorCode、statusCode）。

面試這樣答

30 秒版本

「我使用 try…catch 時有幾個原則：第一，只在能處理的層級 catch，不在每個函式都包一層；第二，catch 到處理不了的錯誤要 re-throw，不能吞掉；第三，用 finally 做資源清理，例如關閉 loading 狀態。非同步的部分用 async/await 搭配 try…catch，效果與同步一致。整個原則是：錯誤應在最了解它的那一層被處理，而不是到處 catch 又到處忽略。」
