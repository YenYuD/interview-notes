程式碼組織：讓六個月後的你不用猜

面試問「你怎麼組織程式碼」，考的是你對關注點分離（SoC）的理解。模組化、命名慣例、Linting——這不是品味問題，而是工程紀律。

分層結構

按職責分層，不是按類型堆砌

src/
├── components/     # UI 元件（React/Vue）
│   └── Header/
│       ├── Header.tsx
│       └── Header.css
├── services/       # API 呼叫、商業邏輯
│   └── apiService.ts
├── hooks/          # 可重用的自訂 Hook（React）
├── utils/          # 純函式工具，無副作用
│   └── formatDate.ts
├── types/          # TypeScript 型別定義
└── store/          # 全域狀態（Redux / Zustand）
關鍵原則：每個資料夾只做一件事。utils/ 裡不該有 API 呼叫；services/ 裡不該有 JSX。邊界清楚，重構才容易。
命名與工具

命名慣例 + 自動化品質守門

對象慣例原因
React 元件 PascalCase（UserCard.tsx） JSX 需要大寫開頭才識別為元件
函式 / 變數 camelCase（getUserById） JS 標準慣例
常數 UPPER_SNAKE（MAX_RETRY） 視覺上一眼認出是不可變常數
資料夾 kebab-case 或 camelCase 避免 macOS/Windows 大小寫差異造成問題
ESLint程式碼規則強制執行
Prettier格式統一，不再爭論縮排
Husky + lint-stagedcommit 前自動跑 lint/test
延伸追問

面試官可能再追

功能導向（Feature-based）vs 類型導向（Type-based）資料夾結構，你怎麼選？

小專案用類型導向（components/、services/）夠清楚；大型專案用功能導向（auth/、dashboard/、profile/），讓同一功能的所有檔案都在一起，避免跨資料夾頻繁跳轉，也更適合微前端架構。

barrel file（index.ts 重新匯出）的優缺點？

優點：import { UserCard, UserList } from '@/components' 路徑簡潔。缺點：若 index.ts 匯出所有東西，可能阻礙 Tree Shaking，且循環依賴更難察覺。大型專案建議只在模組邊界用 barrel，不是每個資料夾都加。

面試這樣答

30 秒版本

「我組織程式碼的核心是關注點分離：UI 元件、API 服務、工具函式分層存放，每層只做一件事。命名上遵循 PascalCase/camelCase 慣例，並用 ESLint + Prettier 確保整個團隊的程式碼風格一致。規模再大一點我會採用功能導向（Feature-based）資料夾結構，讓同一功能的所有檔案聚在一起，重構時不用四處尋找。」
