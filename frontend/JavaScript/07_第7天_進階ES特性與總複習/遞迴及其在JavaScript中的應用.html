JAVASCRIPT / 演算法基礎

函式呼叫自己，
直到問題小到能直接回答

遞迴把大問題拆成相同結構的小問題，直到碰到基底條件（base case）就停止。DOM 樹遍歷、深度優先搜尋、分治演算法，都是遞迴的天然棲息地。

核心結構

每個遞迴函式必須有兩件事

基底條件直接回傳答案，終止遞迴
遞迴條件用更小的輸入呼叫自身，逼近基底
// 階乘：n! = n × (n-1)!
function factorial(n) {
  if (n === 0) return 1;          // 基底條件
  return n * factorial(n - 1);    // 遞迴條件
}
factorial(4); // 24  (4×3×2×1)
✕

忘記基底條件 → 無限遞迴 → stack overflow（RangeError: Maximum call stack size exceeded）。

實務應用

遞迴最自然的三個場景

1

DOM / 樹狀結構遍歷

子節點數量不定、深度不定，遞迴比迴圈更直覺。

2

分治演算法（快速排序、合併排序）

把陣列拆一半遞迴處理，再合併。

3

JSON / 巢狀物件深層操作

深度複製、深度比較、深度搜尋鍵值，都靠遞迴走訪任意深度。

// 深度扁平化陣列（任意層）
function deepFlat(arr) {
  return arr.reduce((acc, val) =>
    acc.concat(Array.isArray(val) ? deepFlat(val) : val), []);
}
deepFlat([1, [2, [3, [4]]]]); // [1, 2, 3, 4]
效能：尾遞迴 vs 記憶化

避免爆 call stack 的兩種策略

技術做法適用場景
尾遞迴（Tail Call）遞迴呼叫放在函式最後一步，引擎可優化成迴圈JS 引擎支援有限（Safari 才有 TCO）
記憶化（Memoization）快取已算過的結果，避免重複計算費氏數列等有大量重複子問題的場景
Trampoline將遞迴改成回傳 thunk，迴圈驅動需要真正避免 stack overflow 時
 
// 記憶化費氏數列 O(n) vs 純遞迴 O(2^n)
function fib(n, memo = {}) {
  if (n <= 1) return n;
  if (memo[n]) return memo[n];
  memo[n] = fib(n - 1, memo) + fib(n - 2, memo);
  return memo[n];
}
延伸追問

面試官可能再追

遞迴和迴圈在效能上有什麼差異？

每次遞迴呼叫都會在 call stack 推入一個新的 stack frame（含局部變數、返回位址），因此記憶體消耗通常比等價的迴圈更高。深度很大時（例如 10,000+ 層）有爆 call stack 的風險。現代 JS 引擎對尾遞迴的 TCO 優化支援不一，通常把深度遞迴改寫成迴圈或用 Trampoline 更穩妥。

什麼是 mutual recursion（相互遞迴）？

函式 A 呼叫函式 B，函式 B 再呼叫函式 A，形成循環。例如判斷奇偶數：isEven(n) → isOdd(n-1) → isEven(n-1)…。同樣需要明確的基底條件，否則也會 stack overflow。

30 秒版本

「遞迴是函式呼叫自身來解決問題，需要兩個必要條件：基底條件（直接回傳，終止遞迴）和遞迴條件（縮小問題範圍再呼叫自身）。最適合用在結構上天然遞迴的問題，例如 DOM 遍歷、深度複製、快速排序。效能上要注意 call stack 深度，對有大量重複子問題的場景（如費氏數列）要加上記憶化把時間複雜度從指數降到線性。」
