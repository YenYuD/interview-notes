三種「等一下再跑」，執行順序卻大不同

process.nextTick 比微任務還快；setImmediate 在目前事件迴圈階段結束後才跑；setTimeout(fn, 0) 更後面。不懂順序，debug 容易翻車。

優先順序

Node.js 非同步執行的先後

① 同步程式碼跑完，呼叫堆疊清空。
② process.nextTick 佇列：清空全部（Node 專屬，比微任務還早）。
③ 微任務佇列：Promise.then 等，全部清空。
④ 巨任務：setImmediate（check 階段）、setTimeout/setInterval（timers 階段），依事件迴圈 phase 順序。
setTimeout(() => console.log('setTimeout'), 0);
setImmediate(() => console.log('setImmediate'));
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('Promise'));

// 輸出：nextTick → Promise → setTimeout/setImmediate（後兩者順序可能互換）
三者比較

各自的定位與使用情境

API環境觸發時機常見用途
setTimeout(fn, 0)通用至少 0ms 後（巨任務）延後執行、給 UI 更新插入空隙
setImmediate(fn)Node.jsI/O 回呼後、timers 之前的 check 階段I/O 密集場景，避免 timer 不確定性
process.nextTick(fn)Node.js目前操作完成後、任何 I/O 前確保回呼在 API 返回後、下一次事件迴圈前執行
⚠️

setImmediate 和 process.nextTick 都是 Node.js 專屬——瀏覽器環境沒有這兩個 API。面試若問這題，通常是針對 Node.js 場景。

延伸追問

面試官可能再追

setTimeout(fn, 0) 和 setImmediate 哪個先跑？

在主模組（非 I/O 回呼內）呼叫時，順序不確定——取決於 timer 精度。但在 I/O 回呼內部呼叫時，setImmediate 一定先於 setTimeout，因為 check 階段在 timers 階段之前。

process.nextTick 濫用有什麼風險？

和微任務一樣，若在 nextTick 回呼中持續加入新的 nextTick，會餓死後面的微任務和巨任務，導致 I/O 事件永遠無法執行。

面試這樣答

30 秒版本

「三者的執行優先順序：process.nextTick 最快，在目前操作完成後、任何 I/O 前執行；接著是 Promise（微任務）；再來才是巨任務——其中 setImmediate 在 I/O 回呼後的 check 階段執行，setTimeout 在 timers 階段。在 I/O 回呼內，setImmediate 會在 setTimeout 之前執行；在主模組兩者順序不確定。」
