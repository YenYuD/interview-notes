阻塞還是讓行？同步與非同步的根本差異

同步程式碼排隊等、一個跑完才跑下一個；非同步程式碼把耗時任務交出去，主執行緒繼續忙，等結果回來再處理。這是理解整個 JS 非同步體系的起點。

核心對比

同步 vs 非同步

同步（Synchronous）非同步（Asynchronous）
執行方式逐行，等前一步完成發出後繼續執行，完成時回呼
主執行緒被阻塞不阻塞，繼續執行
適用場景CPU 計算、資料轉換網路請求、檔案 I/O、計時器
問題長時間操作會凍結 UI結果順序不可預期，需明確處理
執行順序

非同步的「輸出順序」讓人意外

console.log('A');                  // 同步：立刻印

setTimeout(() => {
  console.log('B');               // 非同步：進巨任務佇列
}, 0);

Promise.resolve().then(() => {
  console.log('C');               // 非同步：進微任務佇列
});

console.log('D');                  // 同步：立刻印
// 輸出：A → D → C → B
💡

記住優先順序：同步 → 微任務（Promise）→ 巨任務（setTimeout）。面試最常考這道題的輸出順序。

為何需要非同步

瀏覽器只有一條主執行緒

JS 在瀏覽器中是單執行緒：JS 執行期間，畫面渲染、使用者點擊全部暫停。若用同步方式等待 API 回應，使用者會看到「卡頓」甚至「無回應」。

同步阻塞（危險） 讀取大型資料時 UI 凍結，使用者無法點擊任何東西。
非同步非阻塞（正確） 把 I/O 交給瀏覽器 Web API，主執行緒繼續處理 UI，完成後再把回呼排入佇列。
async 函式不是在不同執行緒執行——它仍在主執行緒上，只是透過事件迴圈讓出控制權。真正的平行處理需要 Web Workers。
延伸追問

面試官可能再追

async 函式是「真的非同步」嗎？

async 函式的同步部分仍在主執行緒同步執行，直到遇到第一個 await 才讓出控制。讓出後，await 後面的程式碼進入微任務佇列，等 Promise resolved 才繼續。

如何在 JS 實現真正的平行（parallel）？

使用 Web Workers（瀏覽器）或 Worker Threads（Node.js）——它們在獨立執行緒運行，透過 postMessage 與主執行緒通訊，適合 CPU 密集型計算。

面試這樣答

30 秒版本

「同步函式會阻塞主執行緒，前一步完成才執行下一步；非同步函式把耗時操作交給瀏覽器 Web API，主執行緒繼續執行，完成後透過事件迴圈把回呼排入佇列。JS 是單執行緒，若用同步方式等待 I/O，UI 會凍結。所以網路請求、計時器都應該非同步處理，用 Promise 或 async/await 管理結果。」
