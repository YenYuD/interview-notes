測試

測試要像說明書，不是像偵探謎題

好的測試能讓三個月後的你（或新同事）一眼看懂：這段程式碼要做什麼、在什麼條件下、預期結果是什麼。壞的測試是維護地雷。

AAA 模式

最重要的結構原則

Arrange → Act → Assert 三段式讓每個測試職責清晰：

test('正確計算兩數之和', () => {
  // Arrange — 準備資料
  const a = 1, b = 2;

  // Act — 執行被測行為
  const result = add(a, b);

  // Assert — 驗證結果
  expect(result).toBe(3);
});
段落之間空一行，一眼就看清楚哪裡是設定、哪裡是執行、哪裡是斷言。
六個核心原則

每個測試都應該符合

1

一個測試，一個行為

不要在一個 test() 裡測多件事。失敗時你才能立刻知道是哪個行為壞了。

2

測試名稱要像規格書

用「當…時，應該…」或「given…when…then…」格式：'當輸入負數，應該回傳 false'，不要 'test1'。

3

測試彼此獨立

A 測試的狀態不能影響 B 測試。用 beforeEach/afterEach 重置，或避免共用可變狀態。

4

mock 外部依賴，不要 mock 被測邏輯

API、DB、時間、亂數這些不可控的才 mock；核心業務邏輯要真實執行才有測試意義。

5

先寫失敗的測試再修 bug

用測試重現 bug，確認紅燈後再修。修完變綠燈，這個 bug 永遠不會再偷偷回來。

6

定期刪掉過時測試

測試也有技術債。不再反映功能的測試只會造成混亂，該刪就刪。

清理範例

afterEach 保持測試隔離

afterEach(() => {
  jest.clearAllMocks(); // 清 mock 呼叫記錄
});

// 或更徹底：
afterEach(() => {
  jest.restoreAllMocks(); // 連 spy 也復原
});
延伸追問

面試官可能再追

什麼是 FIRST 原則？

Fast（快）、Independent（獨立）、Repeatable（可重複）、Self-validating（自我驗證）、Timely（及時寫）。這是評估一個測試是否健康的五個維度。

測試太多了導致 CI 很慢，怎麼辦？

1. Unit 和 Integration 分開跑，PR merge 時才跑整套。2. 只跑受影響的測試（Jest 的 --changedSince）。3. 並行化執行。4. 審視是否有過多重複的覆蓋——同樣的邏輯不需要三層都測。

面試這樣答

30 秒版本

「我寫測試會遵守幾個原則：AAA 結構讓每個測試目的清楚；一個測試只測一件事，失敗時定位快；測試名稱寫成規格書語氣，說明「在什麼條件下預期什麼結果」。用 afterEach 清 mock 確保測試隔離。遇到 bug 一定先寫失敗測試再修，讓這個 bug 永遠不會偷偷回來。」
