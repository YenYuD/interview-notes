覆蓋率 100%，不代表沒有 Bug

程式碼覆蓋率是指引工具，不是品質保證書。80% 有意義的測試遠比 100% 走形式的測試更有價值。理解覆蓋率的四種面向，才能正確解讀數字。

四種覆蓋率

數字背後代表什麼

類型意義重要性
Statement 語句每一行語句是否跑過基本
Branch 分支if/else、三元運算子的每個分支⭐ 高
Function 函式每個函式是否至少被呼叫過一次中
Line 行每一行原始碼是否執行基本
💡

Branch Coverage 最有意義——光語句 100% 也可能漏掉 else 分支的 bug。

範例說明

同一個函式，不同覆蓋率結果

function isEven(num) {
  if (num % 2 === 0) {
    return true;
  } else {
    return false;
  }
}

如果只測 isEven(2)（偶數路徑），Statement Coverage 是 80%，但 Branch Coverage 只有 50%——else 分支根本沒跑到。同時測 isEven(2) 和 isEven(3) 才達到 Branch 100%。

用 Jest 跑覆蓋率：

jest --coverage

會產出 HTML 報告，標出哪些行/分支沒被覆蓋到（紅色）。

正確心態

覆蓋率的限制

覆蓋率能做到

找到「完全沒測到」的死角

引導你補邊界條件

作為 CI gate（如：低於 80% 就擋

覆蓋率做不到

保證邏輯正確（可以跑過但斷言弱）

驗證業務需求是否被滿足

取代 code review 或靜態分析

⚠️

「為了提高覆蓋率而寫的測試」和「為了防 bug 而寫的測試」是不同的東西。前者只是湊數字。

延伸追問

面試官可能再追

你們專案的覆蓋率門檻設多少？

業界常見 70–80%。太低沒保護力，太高（強制 100%）會讓開發者為了指標寫無意義的測試。建議設 Branch Coverage 門檻，比 Statement Coverage 更有意義。

Istanbul 是什麼？和 Jest 是什麼關係？

Istanbul（現在叫 nyc）是 Node.js 覆蓋率工具。Jest 內部用 Istanbul 來計算覆蓋率，跑 jest --coverage 其實是呼叫 Istanbul 產出報告。你不需要另外裝 Istanbul，Jest 已經包含。

面試這樣答

30 秒版本

「覆蓋率是指引，不是目標。我看覆蓋率主要是找沒被測到的死角，特別是 Branch Coverage——只測 if 沒測 else 是很常見的漏洞。實務上我會把 Branch Coverage 設在 CI 的 70–80% 門檻，低於就 fail build。但100% 覆蓋率不代表沒 bug，還是要確保斷言夠強、邊界條件都有測到，而不只是讓程式碼跑過去。」
