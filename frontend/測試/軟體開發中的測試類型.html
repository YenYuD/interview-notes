測試

四種測試類型：從函式到使用者的完整防線

Unit、Integration、System、Acceptance——四層測試各有不同的驗證對象。懂得區分它們，才能在有限資源下做出正確的測試策略。

四層一覽

從小到大，從快到慢

類型驗證對象執行者自動化
Unit 單元個別函式或元件開發者✅ 全自動
Integration 整合模組/服務間的互動開發者✅ 全自動
System 系統完整整合後的整個系統QA 團隊部分自動
Acceptance 驗收是否符合業務需求（UAT）使用者/PM多為手動
各層說明

每層在防什麼問題

U

Unit 單元測試

最小粒度，每個函式獨立測。外部依賴全 mock，速度最快。防：函式邏輯錯誤、邊界值問題。

I

Integration 整合測試

驗兩個以上模組接在一起還能不能合作。例如 API route + Database layer。防：介面不合、資料格式不一致。

S

System 系統測試

部署到測試環境後，對整個系統做黑盒測試（不看程式碼內部）。防：環境設定問題、服務整合後的非預期行為。

A

Acceptance 驗收測試（UAT）

由業務方確認：「這是我要的嗎？」。通常是上線前最後一關。防：開發偏離業務需求。

延伸追問

面試官可能再追

System 測試和 E2E 測試是同一件事嗎？

不完全是。E2E 強調使用者操作流程（從前端到後端全通）；System 測試強調整個系統符合「需求規格」。E2E 可以視為 System 測試的一種實作方式。

小團隊沒有 QA，測試策略怎麼調整？

把 System 測試層合併進 E2E（Cypress/Playwright 跑關鍵流程），由開發者維護。把驗收測試簡化成 demo 給 PM 確認。重心還是放在 Unit + Integration，這兩層 ROI 最高。

面試這樣答

30 秒版本

「軟體測試我分四層：Unit 測函式邏輯、Integration 測模組串接、System 測部署後整體行為、Acceptance 確認符合業務需求。越靠上層越貼近真實使用者，但也越慢越難自動化。實務上我會把大部分精力放在 Unit 和 Integration，System 用 E2E 工具覆蓋關鍵流程，Acceptance 讓 PM 在 staging 環境確認。」
