TDD：先紅後綠，再重構的開發節奏

Test-Driven Development 不只是一種測試技巧，更是設計思維——先想清楚「我的程式碼該怎麼被使用」，才開始實作。紅→綠→重構，三步一循環。

Red-Green-Refactor

三步循環

紅

Red：先寫一個會失敗的測試

功能還沒實作，測試必定失敗（紅燈）。這一步確認測試本身是有效的——如果一開始就通過，測試可能沒有在測正確的東西。

test('adds 1 + 2 to equal 3', () => {
  expect(add(1, 2)).toBe(3); // add 未定義，紅燈
});
綠

Green：寫讓測試通過的最小程式碼

不求完美，只求通過。這步強迫你聚焦在當前需求，不過度設計。

function add(a, b) {
  return a + b; // 最小實作，綠燈
}
重構

Refactor：在測試保護下改善設計

重構命名、抽共用函式、改資料結構——測試是安全網，大膽改。改完確認測試仍然全綠。

💡

每個循環盡量小步前進（5~15 分鐘完成一個紅→綠→重構）。步子太大會讓 debug 變難。

TDD 和 BDD 的差別？

TDD 聚焦在技術行為（函式輸入輸出）；BDD（Behaviour-Driven Development）聚焦在業務行為（Given-When-Then 語法），讓非工程師也能讀懂。兩者不互斥，BDD 是 TDD 的延伸。

什麼情況不適合 TDD？

UI 原型設計、實驗性探索階段、需求極度不確定時。先快速做出可視化結果再補測試是務實選擇。TDD 最有價值的場景是：核心業務邏輯、演算法實作、API 設計。
