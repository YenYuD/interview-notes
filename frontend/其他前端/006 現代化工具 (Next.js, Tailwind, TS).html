Next.js App Router

Pages Router vs App Router，為什麼要換？

Pages Router（舊）App Router（Next.js 13+）
路由檔案pages/about.tsxapp/about/page.tsx
預設元件類型Client ComponentServer Component（RSC）
資料取得getServerSideProps / getStaticProps直接在 Server Component 裡 async/await
Layout 巢狀需自行處理原生 layout.tsx 巢狀
💡

App Router 中，只在真正需要互動（useState、事件監聽）的元件最頂層加 "use client"，把其餘元件保持為 Server Component，才能最大化 RSC 效益。

Tailwind & TypeScript

兩個常問的取捨題

T

Tailwind CSS：Utility-first 的取捨

優點：開發快（不用想 class 名）、Bundle 小（PurgeCSS 自動移除未用樣式）、設計一致性高。
缺點：HTML 標籤冗長、需要學習 class 語法對照表、複雜樣式需搭配 @apply 或 CVA。

TS

interface vs type：使用時機

interface：定義物件結構或 class 形狀，支援聲明合併（Declaration Merging），適合定義 API response、component props。
type：更靈活，可用於 Union、Intersection、Tuple、條件型別。定義「複雜組合型別」時選 type。

ℹ️

多數 TypeScript 風格指南（包含 React 官方）建議：預設用 interface，遇到 interface 做不到的才換 type。

延伸追問

面試官可能再追

RSC 和 SSR 有什麼不同？

SSR 是在伺服器生成 HTML 字串送給瀏覽器，元件程式碼仍然包含在 Client Bundle 做 Hydration。RSC 只在伺服器執行，程式碼完全不進 Client Bundle，沒有 Hydration 成本；但 RSC 不能有互動（useState/事件）。兩者可以共存。

Tailwind 如何搭配 shadcn/ui 這類元件庫？

shadcn/ui 把元件原始碼直接複製到專案（不是 npm 安裝），用 Tailwind + CVA 管理樣式變體，讓你完全掌控樣式，不受第三方 CSS 封裝限制。

TypeScript 的 Generic 泛型如何用在 API 層？

定義一個泛型 response wrapper：type ApiResponse<T> = { data: T; error?: string }，配合 fetch 函式 async function get<T>(url: string): Promise<ApiResponse<T>>，讓每個 API 呼叫都有型別安全的回傳值。
