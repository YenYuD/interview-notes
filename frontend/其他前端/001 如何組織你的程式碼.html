程式碼怎麼放，決定未來能不能改

組織程式碼不只是「放哪個資料夾」，而是讓每個模組只做一件事、依賴方向可預測。好的結構讓你三個月後還看得懂自己寫的東西。

核心原則

三個問題定架構

1

單一職責

一個模組只做一件事。userService.ts 處理使用者業務邏輯，userApi.ts 處理 HTTP 呼叫——不要混在一起。

2

依賴方向

UI 依賴 Service，Service 依賴 API 層——依賴只能往下，不能反過來。這讓你換掉某一層時，其他層不受影響。

3

Feature-based vs Layer-based

小專案用按層（components/、hooks/、utils/）；大專案改用按功能（features/auth/、features/cart/）避免跨資料夾追蹤。

常見結構對比

Layer-based vs Feature-based

方式資料夾長這樣適合何時
Layer-basedcomponents/ hooks/ utils/ api/小型專案、功能少於 5 模組
Feature-basedfeatures/auth/ features/cart/中大型、多人維護、功能增長快
混合式features/ + 共用 shared/多數 React 中型專案的選擇
💡

Feature-based 的關鍵：每個 feature 資料夾只對外暴露一個 index.ts（barrel export），其餘視為私有。

延伸追問

面試官可能再追

什麼是 Colocation？

把「一起變動的東西放在一起」，例如把 component 的測試檔、樣式放在同一資料夾，而不是集中在頂層 __tests__/。這讓改一個 component 時，相關檔案一眼可見。

如何避免 barrel file 造成 Tree Shaking 失效？

避免在 index.ts 中重新匯出整個套件（export * from './utils'）。必要時改用 named re-export，讓 bundler 能靜態分析用到哪些 export。

大型 monorepo 怎麼組織？

用 Turborepo 或 Nx，把共用邏輯抽成 packages/，各應用放 apps/。跨 package 依賴由工具管理，避免直接 import 相對路徑。

面試這樣答

30 秒版本

「我通常用功能導向（Feature-based）組織程式碼：每個功能模組有自己的 components、hooks、API 層，對外只暴露一個 index.ts。共用邏輯抽到 shared/。這樣依賴方向清楚，改一個功能不會意外影響其他模組，新人也容易找到對應程式碼。」
