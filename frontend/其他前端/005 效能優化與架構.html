CSR、SSR、SSG：選錯渲染策略，效能和 SEO 都輸

這三種渲染方式各有場景，面試官要的不是背定義，而是你能說出取捨理由。React 效能優化也是同理——先知道「為什麼慢」，才能選對工具。

渲染策略比較

CSR / SSR / SSG 一眼看清楚

策略渲染時機優點缺點適用場景
CSR 瀏覽器下載 JS 後 互動感強、伺服器壓力低 SEO 差、首屏慢（白屏） 管理後台、登入後頁面
SSR 每次請求時伺服器動態生成 SEO 好、首屏快 伺服器壓力大、TTFB 較高 動態新聞、個人化頁面
SSG Build time 預先生成靜態 HTML 速度極快、CDN 友善 內容更新需重新 build 部落格、電商首頁、文件站
💡

Next.js 支援混合策略：同一個應用可以部分頁面 SSG、部分 SSR，甚至每個元件選擇是 Server Component 還是 Client Component。

React 效能優化

四招減少不必要的渲染

1

React.memo / useMemo / useCallback

props 沒變就跳過重渲染（memo）、快取計算結果（useMemo）、快取函式引用（useCallback）。不要亂加——無效 memo 有開銷，先 profile 再優化。

2

Code Splitting

用 React.lazy + Suspense 做路由層級的懶載入，減小初始 Bundle size，加快首屏。

3

正確的 key 與虛擬滾動

列表 key 用穩定 ID；渲染萬筆資料時用 react-window / react-virtual 只 render 可見範圍。

4

避免 props 傳匿名函式

<Btn onClick={() => ...}> 每次 render 都是新函式，導致子元件即使 memo 也白搭。改用 useCallback 包裝。

延伸追問

面試官可能再追

ISR（Incremental Static Regeneration）是什麼？

Next.js 的第四種策略：SSG 頁面在 revalidate 時間過後，下一次請求時伺服器背景重建，使用者先看舊快取。兼顧速度與資料新鮮度，適合每隔幾分鐘更新的頁面（如新聞列表）。

React.lazy 的限制？

只支援 default export 的元件。需搭配 Suspense 提供 fallback，且不支援 SSR（需用 Next.js 的 dynamic import 取代）。

如何找到哪個元件導致效能問題？

用 React DevTools 的 Profiler 錄製，找 render 耗時長的元件；用 Chrome Performance 找 Long Task；用 why-did-you-render 函式庫找不必要的重渲染。先量測再優化。

面試這樣答

30 秒版本

「選渲染策略我看三個維度：SEO 需求、資料更新頻率、互動程度。管理後台 SEO 不重要選 CSR；部落格或電商首頁選 SSG 最快；動態個人化且需要 SEO 的選 SSR。React 效能優化我優先看 Code Splitting 減小 Bundle，再用 React DevTools 找真正的熱點，才針對性加 React.memo / useCallback，避免無謂的優化成本。」
