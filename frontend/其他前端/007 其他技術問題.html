Redux、CLS、SEO、Git Flow——面試雜科快速備戰

這四題分散在不同領域，共同點是「考你的廣度與實務經驗」。面試官想確認你不只寫元件，也懂狀態管理、效能指標、SEO 與版控流程。

狀態管理

Redux 單向資料流

1

View 觸發 Action

使用者操作或 API 回應，dispatch 一個描述「發生了什麼」的 Action 物件。

2

Reducer 計算新 State

純函式，根據 Action type 和目前 state 計算出新 state——不能有 side effect。

3

Store 更新，View 重新渲染

訂閱 Store 的元件收到通知，React 重新渲染對應的 UI。

ℹ️

現代 Redux 推薦 Redux Toolkit（RTK），用 createSlice 自動產生 action creators，避免手寫大量樣板程式碼。

效能指標 & SEO

CLS 與 SEO 開發要點

主題重點
CLS（Cumulative Layout Shift） 衡量頁面載入時元素突然位移的程度，分數應 < 0.1。常見原因：圖片沒設寬高、遲來的廣告、動態插入內容。
SEO — 語意化 HTML 正確使用 h1~h6（一頁只有一個 h1）、article / section / nav / main，讓爬蟲理解內容結構。
SEO — Meta Tags title（每頁唯一）、description（160 字內）、Open Graph（社群分享預覽）。
SEO — Core Web Vitals LCP（最大內容渲染）< 2.5s；CLS < 0.1；FID/INP（互動反應）< 200ms。Google 排名因素。
💡

防止 CLS 最快的方式：圖片永遠標 width/height，讓瀏覽器在圖片載入前就預留空間。

版控策略

Git Flow 分支職責

分支職責合併目標
main穩定可發布版本，每個 commit 都能上線—
develop開發主線，整合各功能main（發版時）
feature/*個別新功能開發develop
release/*發版前 QA 與最後修正main + develop
hotfix/*緊急修復線上問題main + develop
⚠️

Git Flow 適合有固定發版週期的傳統專案。若團隊做 CI/CD 持續部署，更常用簡化的 Trunk-based Development（短暫 feature branch → 快速合回 main）。

延伸追問

面試官可能再追

Redux 和 Context API 的差別？何時選哪個？

Context 適合低頻率更新的全域資料（主題、語言、登入使用者）；Redux 適合複雜的頻繁更新、需要 time-travel debugging、或多個元件高度互動的狀態。Context 每次更新會讓所有消費者 re-render，Redux 透過 selector 做更細的訂閱。

如何改善 LCP（最大內容渲染）？

預載最大元素（<link rel="preload">）、使用 CDN、圖片格式改 WebP / AVIF、Server-side rendering 首屏內容、避免 render-blocking 資源。

面試這樣答

30 秒版本

「Redux 是單向資料流：View dispatch Action，Reducer 算出新 State，Store 通知 View 更新。現在我用 Redux Toolkit 減少樣板。SEO 方面，我注重語意化 HTML、Meta Tags、Core Web Vitals——尤其是 CLS 低於 0.1，常見做法是圖片設定寬高避免位移。版控用 Git Flow，但 CI/CD 環境會改用 Trunk-based 加快迭代速度。」
