Web 安全 · 工具鏈

把安全掃描埋進 CI/CD，讓機器先抓漏洞

安全漏洞靠人工 review 難以全面覆蓋。靜態分析（lint 時）、依賴掃描（PR 時）、動態測試（staging 時）三層工具形成防護網，讓問題在合併前就被發現。

三層工具矩陣

在哪個階段用哪種工具

層次工具抓什麼何時跑
靜態分析 SAST ESLint + eslint-plugin-security 危險函式（eval、innerHTML）、不安全 regex 本機開發、pre-commit
依賴掃描 SCA npm audit、Snyk 第三方套件已知 CVE CI/CD 每次 PR
動態掃描 DAST OWASP ZAP、Burp Suite 執行時 XSS、CSRF、注入，模擬真實攻擊 staging 環境定期
快速上手

ESLint + npm audit 的 CI 整合

# 安裝 ESLint 安全外掛
npm install eslint eslint-plugin-security --save-dev

# .eslintrc.json
{
  "plugins": ["security"],
  "extends": ["plugin:security/recommended"]
}

# CI 流程中跑依賴漏洞掃描（有高危漏洞就讓 CI 失敗）
npm audit --audit-level=high

# 或用 Snyk（更詳細的修復建議）
snyk test --severity-threshold=high
ℹ

SonarQube 適合大型專案，可在 CI 中設定 Quality Gate，超過漏洞門檻就阻止合併。對小型 JS 專案，ESLint 安全外掛 + npm audit 已經夠用且成本低。

人工補強

工具掃不到的，靠 Code Review

業務邏輯漏洞工具看不懂「這個用戶不應該看別人的訂單」這種邏輯
不安全的資料流追蹤使用者輸入從哪裡來、最後輸出到哪裡（taint analysis）
OWASP Top 10 清單每次 review 對照，確保常見弱點都有被考慮到
延伸追問

面試官可能再追

npm audit 修不乾淨，依賴的依賴有漏洞怎麼辦？

先評估影響：漏洞所在的程式碼是否實際被執行？能否用 npm audit fix --force（有 breaking change 風險）？或在 package.json 的 overrides（npm v8+）強制指定安全版本。

動態掃描（DAST）有沒有誤報問題？

有，OWASP ZAP 等工具對複雜的 SPA 有時會漏掉需要登入才能到達的頁面。需搭配 authenticated scan（設定登入流程腳本）才能掃到保護後的頁面。

面試這樣答

30 秒版本

「我用三層工具防護：開發階段用 ESLint + eslint-plugin-security 靜態分析，抓危險函式使用；CI/CD 跑 npm audit 或 Snyk 掃第三方套件的 CVE，有高危漏洞就阻止合併；staging 定期用 OWASP ZAP 做動態滲透測試。工具之外，Code Review 時我會對照 OWASP Top 10 確認業務邏輯層面的漏洞沒有被漏掉。」
