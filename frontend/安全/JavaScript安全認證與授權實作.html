Web 安全 · 認證授權

Token 存哪、怎麼驗——認證設計決定了攻擊面大小

認證（你是誰）與授權（你能做什麼）是 Web 安全的核心。JWT 存放位置、token 過期策略、RBAC 粒度這三個決策直接決定你的應用程式有多容易被打穿。

Token 存放策略

localStorage、sessionStorage、Cookie 怎麼選

存放位置XSS 風險CSRF 風險建議
localStorage高（JS 可讀）無避免存敏感 token
sessionStorage高（JS 可讀）無同上，tab 關閉即清
HttpOnly Cookie低（JS 無法讀取）有（需搭配 SameSite）推薦，搭配 SameSite=Lax
// ✅ 推薦：server 設 HttpOnly + Secure cookie
res.cookie('token', token, {
  httpOnly: true,   // JS 無法讀取，防 XSS 偷 token
  secure: true,    // 只走 HTTPS
  sameSite: 'Lax',  // 防 CSRF，允許用戶點連結時帶 cookie
});
JWT 生命週期

短效 Access + 可撤銷 Refresh

1

發行短效 access token（15 分鐘）

簽名時鎖定演算法：{ algorithm: 'HS256' }，絕不接受 alg: none。

2

Refresh token 存 DB（30 天）

存在 DB 才能撤銷。被偷或強登出時直接刪掉那筆記錄。

3

Refresh token rotation

每次換新 access token 時，舊的 refresh token 作廢，防止重放攻擊。

⚠

經典漏洞：JWT header 的 alg 欄位設為 "none"，server 若不強制驗算法就會照單全收偽造 token。一定要在 server 端鎖定允許的演算法。

授權控制

RBAC：角色決定能做什麼

// 簡單 RBAC 中介軟體
function requireRole(role) {
  return (req, res, next) => {
    if (req.user?.role === role) return next();
    res.status(403).json({ error: 'Forbidden' });
  };
}

app.delete('/admin/users/:id', requireRole('admin'), handler);
授權應在 server 端強制執行，不能只靠前端隱藏按鈕。用戶可以直接打 API，所以每支 API 都要驗角色或 ownership。

面試官可能再追

OAuth 和自己實作 JWT 有什麼取捨？

OAuth（Google / GitHub 登入）把認證外包給信任的 IdP，省去密碼儲存、社工攻擊等風險，適合 C 端產品。自建 JWT 適合服務間 API 認證或需要完整控制 session 的場景。

如何實作「強登出所有裝置」？

把所有 refresh token 記錄在 DB，登出時刪除或標記失效。若用 JWT access token，可在 DB 維護一個「token 黑名單」（或版本號 tokenVersion），access token 過期前都要比對這個欄位。
