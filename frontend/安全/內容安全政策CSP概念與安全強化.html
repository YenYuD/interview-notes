Web 安全 · CSP

給瀏覽器一份白名單，讓注入的腳本跑不起來

Content Security Policy 是一層設在 HTTP header 的防線，讓瀏覽器只信任你指定來源的資源。就算 XSS 注入成功，腳本沒在白名單裡照樣被攔截。這是縱深防禦的關鍵第二道牆。

核心機制

一行 header，告訴瀏覽器誰可以執行

CSP 透過 HTTP response header 或 <meta> 標籤傳送給瀏覽器，瀏覽器在載入資源前先查白名單，違規的一律阻擋：

# 最基本：只允許同源腳本，禁止 inline script
Content-Security-Policy: default-src 'self'; script-src 'self'

# 常見生產設定：腳本限同源或指定 CDN，圖片放寬
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; img-src *

# meta 標籤方式（不能設 frame-ancestors，安全性略低）
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'">
指令控制什麼資源常用值
default-src所有資源的 fallback'self'
script-srcJavaScript 來源'self' https://cdn.x.com
style-srcCSS 來源'self' 'unsafe-inline'
img-src圖片來源* data:
connect-srcfetch / XHR / WebSocket'self' https://api.x.com
frame-ancestors誰能用 iframe 嵌入（防 Clickjacking）'none'
常見踩雷

開了這些就等於沒開

'unsafe-inline'允許 inline JS/CSS → XSS 依然可注入
'unsafe-eval'允許 eval() → 動態執行字串漏洞
nonce / hash需要 inline 時的安全替代：每次請求帶唯一 nonce
Report-Only 模式先用 Content-Security-Policy-Report-Only 監測，再正式上線
✅

部署策略：先設 Content-Security-Policy-Report-Only + report-uri 收集違規報告，確認不阻塞正常功能後，再換成正式 Content-Security-Policy。

延伸追問

面試官可能再追

CSP 跟 X-Frame-Options 有什麼關係？

X-Frame-Options 只能防 Clickjacking，CSP 的 frame-ancestors 功能相同且更靈活（可允許特定來源），現代瀏覽器兩者並用以向後相容。

React / Vue 應用怎麼設 CSP？

SPA 通常有 inline style/script（如 styled-components），需要設 nonce 或 hash。Webpack / Vite 有對應 CSP plugin 自動生成 nonce。style-src 'unsafe-inline' 是最後手段。

CSP 能防所有 XSS 嗎？

不能 100%。CSP 是縱深防禦的第二層，不能取代第一層的輸出跳脫。攻擊者若能控制白名單內某個 CDN，或利用 JSONP endpoint，仍可繞過。

面試這樣答

30 秒版本

「CSP 是透過 HTTP header 告訴瀏覽器哪些來源的資源才可載入執行，是 XSS 的縱深防禦第二道牆——就算攻擊者成功注入腳本，只要不在白名單裡，瀏覽器就阻擋。設定時我會避免 'unsafe-inline'，改用 nonce；上線前先用 Report-Only 模式收集違規，確認不阻斷正常流程才切換正式模式。」
