Web 安全 · SQL Injection

使用者輸入不該直接拼進 SQL 字串

SQL injection 讓攻擊者透過輸入欄位改寫資料庫查詢邏輯，輕則繞過登入，重則傾洩整張 users 表。根治方法只有一個：把資料和 SQL 指令徹底分離——用參數化查詢，讓 DB 自己負責跳脫。

危險 vs 安全

字串拼接 vs 參數化查詢

// ❌ 危險：字串拼接 — 輸入 ' OR '1'='1 即可登入任何帳號
const query = `SELECT * FROM users WHERE name = '${userInput}'`;
db.query(query);

// ✅ 安全：參數化查詢（mysql2 / pg）— 輸入被當純資料處理
const query = 'SELECT * FROM users WHERE name = ?';
db.query(query, [userInput]);

// ✅ 安全：pg（node-postgres）使用 $1 佔位符
const { rows } = await pool.query(
  'SELECT * FROM users WHERE id = $1',
  [userId]
);
✅

參數化查詢不是「幫你跳脫特殊字元」，而是讓資料庫驅動程式把參數當資料值處理，完全不可能被當成 SQL 指令解析。

ORM 與工具層

讓框架幫你處理

Sequelize / TypeORMORM 預設使用參數化查詢，findAll where 條件自動安全
Prisma所有查詢方法都是類型安全且參數化的
Raw queryORM 也能寫 raw SQL，此時仍需手動用佔位符，不可拼接
// Sequelize ORM — 安全，自動處理
User.findAll({ where: { id: userId } });

// Sequelize raw query — 仍需參數化
sequelize.query('SELECT * FROM users WHERE id = :id',
  { replacements: { id: userId } });
延伸追問

面試官可能再追

前端工程師需要了解 SQL injection 嗎？

需要。前端若直接串接 Firebase / Supabase 等 BaaS，仍需理解 Row Level Security 和查詢規則。全端場景更是必考。面試官問這題是在測你對資料流的安全意識。

除了參數化查詢，還有哪些補充防禦？

最小權限（應用程式 DB 帳號只給必要的 SELECT/INSERT 權限，不給 DROP）、輸入格式驗證（先確認型別合法再查詢）、儲存程序（將查詢邏輯封裝在 DB 層）。但這些都是補充，根本防禦還是參數化查詢。

面試這樣答

30 秒版本

「SQL injection 的根因是把使用者輸入拼接到 SQL 字串裡，讓攻擊者改變查詢邏輯。我的防禦是永遠用參數化查詢，讓資料庫把輸入當純資料而非指令。用 ORM（Sequelize / Prisma）時預設就是安全的，但寫 raw query 時仍要用佔位符。補充的話再加最小權限原則，限制 DB 帳號只有必要的操作權。」
