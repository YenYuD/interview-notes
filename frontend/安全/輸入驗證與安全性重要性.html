Web 安全 · 輸入驗證

所有注入攻擊都有同一個根因：信任使用者輸入

SQL injection、XSS、Command injection——這些攻擊的共同前提是應用程式沒有驗證輸入就直接使用。輸入驗證是安全防線的第一道閘，server 端驗證是唯一真正可靠的保障。

Client vs Server

兩端驗證，各有職責

Client 端驗證即時回饋 UX，能被繞過（開 DevTools 就行），不能作為安全依據
Server 端驗證唯一可靠的安全關卡，任何輸入都必須在 server 重新驗證
// ❌ 只靠 client 端 — 攻擊者可直接送 HTTP request 繞過
<input type="email" required pattern="...">

// ✅ Server 端重新驗證（Node.js + express-validator）
app.post('/submit', [
  body('email').isEmail(),
  body('age').isInt({ min: 0, max: 120 }),
], (req, res) => {
  const errors = validationResult(req);
  if (!errors.isEmpty()) return res.status(400).json({ errors });
  // 繼續處理已驗證的輸入
});
驗證策略

白名單 vs 黑名單，淨化 vs 拒絕

策略作法適用情境
白名單驗證只接受符合規則的格式（如 email regex、isAlphanumeric）結構化欄位（帳號、電話、日期）
淨化 Sanitize移除／轉義危險字元，保留內容需允許 HTML 輸入的富文字欄位
拒絕黑名單過濾 <script> 等關鍵字不推薦，攻擊者容易繞過
⚠

注意長度與型別：驗證格式還不夠，還要限制字串長度（防緩衝區溢位）、型別（數字欄位確認是整數），以及必填欄位不為空。

延伸追問

面試官可能再追

輸入驗證和輸出跳脫有什麼不同？

驗證是在進入系統時確認格式合法；輸出跳脫是在呈現到頁面時把特殊字元轉換為安全文字。兩者互補，缺一不可——驗證擋不住所有非法字元，輸出跳脫才是 XSS 的根本防禦。

使用 ORM 還需要輸入驗證嗎？

仍需要。ORM 防 SQL injection，但不防 XSS（輸出問題）、不防業務邏輯錯誤（如年齡為負數）。驗證層和 ORM 解決不同問題。

面試這樣答

30 秒版本

「幾乎所有注入攻擊都是因為信任使用者輸入造成的。我的原則是：client 端驗證只為 UX，server 端驗證才是安全關卡，兩者都必須做。策略上優先用白名單（只接受已知合法格式），需要 HTML 輸入才用 sanitize-html 等函式庫淨化。輸入驗證是第一道防線，但不能取代輸出跳脫和參數化查詢——各層各司其職。」
