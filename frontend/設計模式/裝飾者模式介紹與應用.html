Design Patterns

不修改原始碼，動態疊加行為

裝飾者模式透過「包裝」物件來擴展功能，讓你在不動原始類別的情況下組合新行為。React 的 HOC 和 JavaScript 的 Class Decorator 都是它的直接體現。

核心概念

層層包裝，介面一致

裝飾者與被裝飾物件實作同一個介面，呼叫端無需知道被包裝了幾層。

// 原始物件
const logger = {
  log: (msg) => console.log(msg)
};

// 裝飾者：加上時間戳
function withTimestamp(logger) {
  return {
    log: (msg) => logger.log(`[${new Date().toISOString()}] ${msg}`)
  };
}

// 裝飾者：加上日誌等級前綴
function withLevel(logger, level) {
  return {
    log: (msg) => logger.log(`[${level}] ${msg}`)
  };
}

const fancy = withLevel(withTimestamp(logger), 'INFO');
fancy.log('hello'); // [INFO] [2026-05-27T…] hello
組合 vs 繼承：裝飾者模式使用組合（composition）而非繼承，避免深層繼承樹帶來的脆弱性。每個裝飾者只關注一件事，符合單一職責原則。
前端應用

HOC 就是裝飾者模式

前端場景裝飾了什麼
React HOC（如 withAuth）包裝元件，注入認證邏輯
TypeScript @decorator包裝 class / method，加 logging / validation
fetch 包裝器在原始 fetch 外包加上 retry、timeout、auth header
Express middleware每個 middleware 就是一層裝飾
✅

React Hooks 時代：HOC 已逐漸被 custom hook 取代，但裝飾者的思維依然存在——useMemo、useCallback 本質上也是包裝原始值以加上記憶化行為。

延伸追問

面試官可能再追

裝飾者模式 vs 繼承，各自的優缺點？

繼承在編譯時期決定，無法動態改變；裝飾者在執行時組合，彈性更高。繼承的優點是程式碼直觀易讀；裝飾者的優點是遵守 OCP，可任意組合，但多層裝飾可能讓除錯困難。

JavaScript Proxy 與裝飾者模式有何關係？

Proxy 是語言層級的裝飾者，攔截對任何物件的操作（get、set、apply 等），不需要實作相同介面。常見用途：響應式資料（Vue 3 的 reactive）、驗證、日誌。裝飾者模式是設計層面的概念，Proxy 是實作裝飾的原生工具之一。

「裝飾者模式透過包裝物件來動態疊加行為，不修改原始類別。裝飾者與被裝飾物件實作同一介面，呼叫端不知道包了幾層。前端最直接的例子是 React HOC：withAuth(Component) 就是裝飾，注入認證邏輯而不改變元件本身。它的核心價值是組合優於繼承——每個裝飾者只負責一件事，任意組合比深層繼承更靈活、更好維護。」
