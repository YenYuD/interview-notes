Design Patterns

把「動作」包成物件，Undo 才可能

命令模式將一個請求封裝成獨立物件，使它可以被排隊、記錄、甚至撤銷（Undo）。前端文字編輯器、GUI 按鈕事件、巨集錄製都靠它。

五個角色

Command 是核心，Invoker 觸發，Receiver 執行

角色職責
Command定義 execute() / undo() 介面
ConcreteCommand實作具體操作，持有 Receiver 參考
Receiver真正執行工作的物件（如 DOM 元素、API 服務）
Invoker持有命令，決定何時觸發 execute()
Client組裝 Command 與 Receiver，交給 Invoker
 
class AddTextCommand {
  constructor(editor, text) {
    this.editor = editor; this.text = text; this.prev = '';
  }
  execute() { this.prev = this.editor.content; this.editor.content += this.text; }
  undo()    { this.editor.content = this.prev; }
}

class History { // Invoker
  constructor() { this.stack = []; }
  execute(cmd) { cmd.execute(); this.stack.push(cmd); }
  undo()       { this.stack.pop()?.undo(); }
}
應用場景

Undo/Redo 是最典型的使用案例

文字編輯器Ctrl+Z 撤銷每個操作
繪圖工具每個筆觸是一個 Command
巨集指令錄製一序列命令後重播
GUI 按鈕按鈕只知道 execute，不知道細節
💡

Redux 就是命令模式：每個 action 就是一個命令物件（含 type + payload），dispatch 是 Invoker，reducer 是 Receiver。Redux DevTools 的 time travel 正是利用命令歷史實現的 Undo。

延伸追問

面試官可能再追

命令模式 vs 策略模式，核心差異？

兩者都封裝「行為」，但目的不同。策略模式關注同一工作的不同演算法（可互換）；命令模式關注把操作變成物件，以支援佇列、記錄、Undo——操作本身是核心，不是為了互換演算法。

如何實作多步 Undo？

維護一個命令 stack：execute 時 push 到 stack；undo 時 pop 最後一個命令並呼叫其 undo()。Redo 則另外維護一個 redo stack。這正是大多數文字編輯器的實作方式。

面試這樣答

30 秒版本

「命令模式把一個請求封裝成包含 execute 和 undo 方法的命令物件。Invoker 持有命令並決定何時執行，Receiver 是真正做事的物件。這樣操作歷史可以存入 stack，要實作 Undo/Redo 只需 pop 命令後呼叫 undo。前端最直接的例子就是 Redux：每個 action 就是一個命令，Redux DevTools 的 time travel 就靠這個機制。」
