Design Patterns

把「如何建立物件」封裝起來

工廠模式讓呼叫端不需要知道要 new 哪個具體類別——只告訴工廠「我要什麼」，工廠決定「給哪個」。解耦建立邏輯是核心價值。

核心概念

從 if/else 到工廠函式

最初可能寫出散落各地的 if (type === 'dog') new Dog()；工廠模式把這段邏輯集中管理，新增類型只改工廠，不動呼叫端。

散落 if/else建立邏輯遍布各處，難維護
工廠函式建立邏輯集中，呼叫端解耦
// ✅ 工廠函式：集中管理物件建立
function createValidator(type) {
  const validators = {
    email:  () => new EmailValidator(),
    phone:  () => new PhoneValidator(),
    postal: () => new PostalValidator(),
  };
  if (!validators[type]) throw new Error(`未知類型：${type}`);
  return validators[type]();
}

const v = createValidator('email'); // 呼叫端不知道也不在意 EmailValidator
前端應用場景

React 元件工廠 / 測試 Mock

場景工廠做什麼
動態渲染不同類型卡片根據 type 回傳對應 React 元件
表單驗證策略根據欄位類型建立對應 Validator 實例
單元測試 mock 工廠集中建立假物件，避免每個測試各自 new
API 資料轉換根據後端 type 欄位建立對應 Model 物件
💡

工廠 vs 建構函式：工廠函式不綁定 this，可以回傳任意物件（包含 Promise）；建構函式強制回傳新實例。TypeScript 中常用工廠函式搭配 Union type 做 discriminated union 的物件建立。

延伸追問

面試官可能再追

工廠模式（Factory）vs 抽象工廠（Abstract Factory）的差別？

工廠模式建立單一類型的物件；抽象工廠建立一整「族」相關物件（如 LightThemeFactory 同時建立 Button、Input、Modal 的淺色主題版本），確保同族物件風格一致。

工廠模式的缺點是什麼？

若建立邏輯簡單，工廠反而增加不必要的抽象層；每新增一種類型仍需修改工廠本身（除非用策略物件或 Registry 模式解耦）。物件類型少時，直接 new 反而更清晰。

面試這樣答

30 秒版本

「工廠模式把物件的建立邏輯集中封裝，讓呼叫端只需提供類型，不需要直接 new 具體類別。好處是當要新增新類型時只改工廠，呼叫端程式碼不動，符合開放封閉原則。前端常見場景是動態元件渲染和表單驗證策略。要注意的是若物件類型少且建立邏輯簡單，直接 new 更清晰，不必強行套用工廠。」
