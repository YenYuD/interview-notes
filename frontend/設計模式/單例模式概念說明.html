Design Patterns

整個程式只能有一個實例

單例模式保證一個類別只被實例化一次，並提供全域存取點。Logger、設定物件、DB 連線池是最常見的應用場景。

核心機制

三個關鍵特性

單一實例只建立一次，後續回傳相同參考
全域存取透過靜態方法 getInstance() 取得
延遲初始化第一次需要時才建立（Lazy init）
class Singleton {
  static #instance = null; // 私有靜態屬性

  static getInstance() {
    if (!Singleton.#instance) {
      Singleton.#instance = new Singleton();
    }
    return Singleton.#instance;
  }

  constructor() { this.createdAt = Date.now(); }
}

const a = Singleton.getInstance();
const b = Singleton.getInstance();
console.log(a === b); // true
ES Module 天生就是單例：同一模組在同一執行環境只會被載入一次，export 的物件即全域唯一。實務上直接 export const logger = new Logger() 就能達到同等效果。

使用場景 vs 陷阱

何時用、何時避免

場景建議
Logger、錯誤追蹤（Sentry）✅ 適合，全程唯一狀態
設定物件（Config）✅ 適合，避免多份設定衝突
資料庫 / WebSocket 連線✅ 適合，節省資源
業務邏輯物件⚠️ 謹慎，易產生隱性共享狀態
單元測試中的依賴❌ 難以 mock，測試間互相污染
⚠️

全域狀態是雙面刃：方便存取但難以追蹤誰修改了狀態；在 React 等元件化框架中，優先用 Context 或狀態管理庫取代裸的 Singleton，保持資料流可追蹤。

延伸追問

面試官可能再追

JavaScript 的 ES Module 如何天然實現單例？

ES Module 在同一 JS 執行環境（同一 realm）只會被求值一次，之後的 import 都得到快取的模組。因此 export const db = new Database() 天生就是單例，不需要手動實作 getInstance。

單例模式對單元測試有何影響？

Singleton 持有全域狀態，測試 A 的副作用可能污染測試 B。解法是在測試前後重置狀態（或注入測試用假物件），或改用依賴注入（DI）讓外部傳入實例，而非讓類別自己管理唯一性。

面試這樣答

30 秒版本

「單例模式確保一個類別只存在一個實例，透過靜態的 getInstance() 方法回傳，後續呼叫都拿到同一個物件參考。常見應用是 Logger、設定物件、DB 連線池。在現代 JavaScript 中，ES Module 本身就是單例——同一模組只會載入一次，所以直接 export 一個實例即可。要注意的是全域狀態讓單元測試難以隔離，需要搭配依賴注入或在測試前後重置狀態。」
