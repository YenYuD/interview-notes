Design Patterns

一對多的訂閱通知機制

觀察者模式讓 Subject（主體） 的狀態改變時，自動廣播給所有已訂閱的 Observer，是事件驅動架構與狀態管理的核心概念。

核心概念

Subject 廣播，Observer 被動接收

觀察者模式定義「一對多」依賴關係：一個 Subject 維護一份觀察者清單，狀態改變時呼叫每個觀察者的 update()。雙方透過介面耦合，不需要知道對方的具體實作。

角色職責前端對應
Subject持有狀態、管理訂閱、觸發通知EventEmitter、Redux store
Observer實作 update()，被動接收通知React component、DOM listener
subscribe觀察者向 Subject 登記addEventListener
unsubscribe取消訂閱，避免記憶體洩漏removeEventListener
實作

最小可運作實作

class Subject {
  constructor() { this.observers = []; }

  subscribe(obs)   { this.observers.push(obs); }
  unsubscribe(obs) {
    this.observers = this.observers.filter(o => o !== obs);
  }
  notify(data) {
    this.observers.forEach(o => o.update(data));
  }
}

class Observer {
  constructor(name) { this.name = name; }
  update(data) { console.log(`${this.name} 收到：${data}`); }
}

const store = new Subject();
const viewA = new Observer('ViewA');
store.subscribe(viewA);
store.notify('price=100'); // ViewA 收到：price=100
💡

前端常見應用：addEventListener 就是觀察者模式的瀏覽器原生實作；React 的 Context、Redux、MobX、RxJS Observable 也都以此為基礎。

延伸追問

面試官可能再追

觀察者模式 vs 發佈/訂閱模式（Pub/Sub）有何不同？

觀察者模式中 Subject 直接持有觀察者清單，雙方互相知道對方存在（鬆耦合但非完全解耦）。Pub/Sub 引入「事件中介者（Event Bus/Broker）」，發佈者與訂閱者完全解耦，互不知道對方存在，適合跨模組、跨系統通訊。

使用觀察者模式時常見的記憶體洩漏問題？

若 Observer 在銷毀前沒有呼叫 unsubscribe，Subject 仍持有其參考，GC 無法回收。React 的 useEffect 清除函式、Vue 的 beforeDestroy 都是對應的防護機制。

React 的 useState / useReducer 算觀察者模式嗎？

廣義上算。React Fiber 是 Subject，持有訂閱該 state 的所有 component；狀態改變時 React 排程 re-render（即通知觀察者）。只是 React 將這層抽象化成 hooks API，開發者不直接操作訂閱清單。
