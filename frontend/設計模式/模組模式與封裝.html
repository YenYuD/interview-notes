Design Patterns

用閉包建立私有狀態，避免全域污染

模組模式利用 IIFE 與閉包創造私有作用域，只把必要的介面暴露出去。在 ES Module 普及之前，這是 JavaScript 管理程式碼組織的主要手段，封裝的思維至今仍適用。

核心結構

IIFE + 閉包 = 私有 / 公開分離

const counter = (function () {
  let _count = 0; // 私有，外部無法直接存取

  function _validate(n) { return Number.isInteger(n); }

  return { // 公開 API
    increment: (n = 1) => {
      if (_validate(n)) _count += n;
    },
    reset: () => { _count = 0; },
    getCount: () => _count,
  };
})();

counter.increment();
counter.getCount(); // 1
counter._count;     // undefined（私有保護）
IIFE（立即執行函式表達式）：(function(){ ... })() 在宣告時立即執行，建立獨立作用域，執行完後作用域消失，但 closure 仍保留對內部變數的參考。
演進歷史

從 IIFE 到 ES Module

時期封裝方式問題
早期 JS（2009 前）全域變數、命名空間物件 MyApp.util容易命名衝突
模組模式時期IIFE + 閉包無法跨文件共用模組
CommonJS（Node.js）module.exports / require同步載入，不適合瀏覽器
ES Module（ES2015+）export / import（原生靜態分析）現代標準，推薦使用
✅

現代建議：今天寫新程式碼優先用 ES Module（export / import）；IIFE 模組模式仍有用武之地——如 bundler 生成的 IIFE bundle、或需要在老瀏覽器上手動隔離作用域的場景。

延伸追問

面試官可能再追

模組模式如何實現「揭示模組（Revealing Module）」變體？

Revealing Module Pattern 在 IIFE 內部定義所有函式（公開和私有），最後的 return 物件只列出要公開的參考，讓公開介面的宣告集中在一處，程式碼更易讀。return { increment, getCount } 而不是在 return 裡定義函式。

ES Module 和 IIFE 模組模式，封裝機制的本質差異？

IIFE 靠函式作用域（closure）隔離；ES Module 靠語言規範保證模組作用域，import 的 binding 是 live binding（即時綁定），IIFE 的 getter 則是主動呼叫。此外 ES Module 是靜態結構，打包工具可靜態分析並做 Tree Shaking；IIFE 模式是動態的，難以靜態分析。

「模組模式利用 IIFE 與閉包建立私有作用域——IIFE 內部的變數和函式外部無法存取，只有 return 出來的公開 API 才能被呼叫。核心目的是封裝私有狀態、避免全域命名污染。現代開發用 ES Module（export/import）取代了手動 IIFE，但模組模式的思維依然重要：理解它有助於理解 Bundler 的 scope hoisting 和 IIFE bundle 輸出格式。」
