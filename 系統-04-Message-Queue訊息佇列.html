API 只把「訂單成立」丟進 queue 就立刻回應使用者；扣款、寄信、通知由各自的 consumer 慢慢做 —— 像餐廳「點完餐先給號碼牌」。
什麼時候該引入

四大用途

削峰突發流量先堆 queue，consumer 按速度消化
解耦A 不用等 B、也不用知道 B 是誰
重試B 暫掛，訊息留著，復原後繼續
廣播一事件多 consumer 各自處理
最重要觀念

Exactly-once 做不到

⚠️

At-least-once（業界主流）：保證至少送達一次，但可能重複。Exactly-once 在分散式系統中理論上做不到 —— 廠商宣稱的其實都是「at-least-once + 冪等保證」包裝出來的。

✅

結論：設計 consumer 時一定假設訊息會重複，靠冪等（用 event id）去重。

選型：業務事件流用 Kafka / RabbitMQ；Node 任務佇列用 BullMQ（Redis-backed）；AWS 用 SQS / Kinesis。

面試這樣答

30 秒版本

「Queue 用在削峰、解耦、重試、廣播 —— 例如 Stripe 續扣失敗，我不會在 webhook 同步做重活，而是丟進 BullMQ 排程處理。關鍵觀念是 exactly-once 在分散式下做不到，主流是 at-least-once，所以 consumer 一定要做冪等去重（用 event id）。選型上業務事件用 Kafka/RabbitMQ，Node 任務佇列用 BullMQ。」
