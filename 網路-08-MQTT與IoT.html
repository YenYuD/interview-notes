為什麼不用 HTTP polling

MQTT 的優勢

  • 超輕量 header：最小 2 bytes（HTTP 動輒幾百 bytes）。
  • 長連線：避免每次重做 TCP + TLS 握手。
  • Retain message：broker 保留 topic 最後一筆，新訂閱者一連上立刻收到目前狀態。
  • Last Will（遺囑）：裝置異常斷線時 broker 自動發預設訊息 → 實現「車輛離線」通知。
  • 省電：對電池供電的裝置至關重要。
📊

一萬台車每 5 秒打一次 HTTP = 約 2000 RPS 純消耗；MQTT 長連線 + 2 bytes header，broker 壓力小非常多。

三種 QoS

可靠度分級

QoS意思用在哪
0最多一次（發了就忘）GPS telemetry（丟一筆無所謂）
1至少一次（可能重複）解鎖指令（一定要到，重複靠應用層 idempotency）
2剛好一次（四段握手，最貴）計費結算
bikes/{bikeId}/telemetry     # 上行：車輛回報 GPS/電量
bikes/{bikeId}/cmd/unlock     # 下行：server 發解鎖指令
bikes/{bikeId}/status         # retain：保留最新狀態
大量 telemetry 不打爆 server

進階策略

  • Batching：broker 收完先寫 queue（如 Kafka），consumer 每秒 batch insert（別每筆 INSERT）。
  • 降採樣：高頻收集、低頻寫入；90 天後只留 1 分鐘平均。
  • Tiering：熱資料 Redis、溫資料 TimescaleDB、冷資料 S3。
  • 離線補傳：裝置端本地 buffer（SQLite），重連後每筆帶 timestamp，server 依 timestamp 排序 + dedup key 去重。
面試這樣答

30 秒版本

「IoT 用 MQTT 是因為長連線 + 2 bytes header + pub/sub + 省電，比 HTTP polling 省太多。QoS：GPS 用 0、解鎖用 1（一定要到，重複靠應用層 idempotency）、計費用 2。再搭 retain 提供最新狀態、Last Will 做離線偵測。寫入 DB 一定 batch、不要每筆 INSERT。」
