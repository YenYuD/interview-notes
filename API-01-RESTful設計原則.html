API 設計

網址當名詞，
動作交給 method

RESTful 的精神：用 HTTP 既有的語意來設計 API。把後端資料想成一間圖書館，URL 是書架上的東西，method 是你要對它做什麼，status code 是館員回你的結果。

直覺類比

圖書館的三件事

角色對應例子
URL書架上的東西（名詞）/books、/books/5
Method你要做什麼（動詞）看(GET)、放新書(POST)、整本換(PUT)
Status館員回你的結果2xx 成功、4xx 你錯、5xx 館員出包
⚠️

所以你不會把動作寫進網址（像 /getBooks、/createBook）—— 動作已經由 method 表達了。

DEMO — 動手組請求

選一個 method，看它的語意

點下面的 method，看它對 /bikes 做什麼、回什麼 status、是不是冪等：

點 method 看語意
GET /bikes
語意
取得所有單車（安全，不改資料）
典型 status / 冪等
200 OK · ✅ 冪等
核心原則

四段口訣

1

資源導向

URL 用名詞、用複數：/bikes、/bikes/:id。巢狀別超過兩層，/users/:id/orders OK，再深就該拆。

2

Method 語意

GET 安全且冪等、POST 建立（非冪等）、PUT 整筆覆寫（冪等）、PATCH 部分更新（看實作）、DELETE 刪除（冪等）。

3

Status 對應業務

建立成功 201 + Location；非同步 202；無內容 204；格式錯 400；業務驗證失敗 422。

4

Stateless 無狀態

每個請求自帶身份（如 JWT），server 不靠記憶上一個請求。

延伸追問

面試官可能再追

為什麼 PATCH 不一定冪等？

{ "increment": 1 } 做兩次會加兩次（非冪等）；{ "status": "active" } 做幾次結果都一樣（冪等）。看 body 怎麼寫。

批次建立算 RESTful 嗎？

嚴格說違反資源導向，但實務接受 POST /bikes/batch 或讓 POST /bikes 收一個陣列。

常見踩雷

這些別做

✕

寫 GET /getBikes、POST /createBike —— 動詞放網址是大忌。

✕

回 200 卻塞 {"error":"..."} —— 錯誤就該回 4xx/5xx，別用 200 包錯誤。

✕

DELETE 同一筆兩次回 500 —— 應回 204 或 404（這正是冪等概念）。

面試這樣答

30 秒版本

「我會照 資源命名 → method 語意 → status code → 無狀態 四段講。URL 用複數名詞像 /bikes，動作交給 method，建立回 201、刪除回 204。每個請求自帶 JWT 保持無狀態。最後用冪等性保護寫入、用統一的錯誤格式回 4xx/5xx。」
