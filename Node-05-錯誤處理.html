try/catch 抓不到的錯

非同步的錯誤 try/catch 不一定抓得到。要懂為什麼，並準備好「Express 錯誤 middleware」和「全域兜底」兩道防線。

DEMO — 同一個 try，兩種結果

為什麼 callback 的錯抓不到？

try/catch 只能抓「當下這個同步執行流」裡的錯。舊式 callback 在未來某個 tick 才被 Event Loop 呼叫，那時 try 早就跑完離開了。async/await 是 Promise 語法糖，await 把後面的程式碼接回同一個錯誤流，所以 catch 得到。
第一道防線

Express 錯誤 middleware（業務層）

app.use((err, req, res, next) => {
  // 「四個參數」是 Express 辨識錯誤 middleware 的方式
  res.status(err.status || 500).json({ code: err.code, message: err.message });
});

任何 middleware 呼叫 next(err) 就會跳到這。Async middleware 要包 wrapper，不然 throw 出來的錯沒人接：

const asyncHandler = (fn) => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);

（Express 5+ 已內建支援 async，但很多專案還在 4.x 要自己包。）

第二道防線

全域兜底（最後一道）

process.on('uncaughtException', (err) => {
  logger.fatal(err);
  process.exit(1);  // 重要：強制重啟，狀態已不可信任
});
process.on('unhandledRejection', (reason) => {
  logger.error(reason);
});
常見踩雷

這些別做

✕

uncaughtException 之後繼續跑 → 狀態已不可信，一定要 exit 讓 process manager 重啟。

✕

一堆 async function 沒 await → 觸發 unhandledRejection 警告。

✕

在 callback 內 throw → Event Loop 接不到。

面試這樣答

30 秒版本

「try/catch 抓不到舊式 callback 的錯，因為 callback 在未來的 tick 才執行，那時 try 區塊早跑完了；async/await 是 Promise 語法糖所以抓得到。實務兩道防線：Express 用四參數的錯誤 middleware 統一處理，async handler 要包 wrapper 把 reject 轉成 next(err)；最後用 uncaughtException 全域兜底，但一定要 process.exit(1) 重啟。」
