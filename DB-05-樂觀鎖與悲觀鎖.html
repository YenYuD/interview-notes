先鎖起來 vs 改時才檢查

兩人同時想預訂同一台車，怎麼保證只有一個成功？悲觀鎖先把車鎖住不准別人動；樂觀鎖不鎖，改的時候才檢查有沒有被別人搶先。

DEMO — 兩人搶同一台車

Amy 和 Bob 同時按預訂

切換鎖策略，按「兩人同時搶」，看誰成功、機制怎麼運作：

先選鎖策略
// 搶車過程會顯示在這…
悲觀鎖：假設衝突常發生，先鎖。樂觀鎖：假設衝突少，不鎖、改時才比對 version。
悲觀鎖（先鎖再改）

SELECT ... FOR UPDATE

BEGIN;
SELECT * FROM bikes WHERE id = ? FOR UPDATE;  -- 鎖住這列
-- 其他交易想改這列只能等
UPDATE bikes SET status = 'reserved' WHERE id = ?;
COMMIT;

適合高衝突場景。缺點：鎖太久會卡住別人。

樂觀鎖（改時才檢查）

用 version 欄位

UPDATE bikes
SET status = 'reserved', version = version + 1
WHERE id = ? AND version = ?;   -- 帶上我讀到的 version
-- 影響 0 筆 → version 已被別人改過 → 衝突 → 重試

適合低衝突場景。不鎖、效能好，但要自己寫 retry 邏輯。

面試這樣答

30 秒版本

「高衝突用悲觀鎖（SELECT FOR UPDATE），先鎖住別人得等，直觀但鎖久會卡；低衝突用樂觀鎖，加 version 欄位、UPDATE 時帶舊 version，影響 0 筆代表被搶先要 retry。搶資源這種高衝突場景我傾向悲觀鎖或 Redis 分散式鎖（SET NX EX），因為衝突明確且要立即裁決。」
