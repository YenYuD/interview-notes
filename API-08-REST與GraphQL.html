API 設計

套餐 vs 自助餐

REST：server 定好每個 endpoint 回什麼（像套餐，多的少的都不能改）。GraphQL：client 自己描述要哪些欄位，server 照單給（像自助餐，不多不少）。

DEMO — over-fetching 有多浪費

我只要名字跟訂單金額…

情境：手機只想顯示「用戶名 + 最近 3 筆訂單金額」。切換看回傳差多少：

先選 API 風格
送出的請求：
GET /users/5
收到的回傳：
REST 回了一堆你不要的欄位（over-fetching），訂單又得再打一支 API（under-fetching）。GraphQL 一次剛好給你要的。
各自適合的場景

怎麼選

GraphQL 適合需求多變 / 弱網省流量 / 聚合多來源(BFF)
REST 適合公開 API / HTTP 快取 / 檔案串流 / 團隊不熟 GraphQL
GraphQL 的痛點

不是免費的午餐

⚠️

N+1 問題：查一個 user 的 orders、再查每個 order 的 items，會打 N 次 DB。解法是 DataLoader（把同 tick 內查詢 batch 起來 + cache）。

⚠️

沒有原生 HTTP cache：查詢全走 POST，CDN/瀏覽器的 GET 快取用不上。

⚠️

Schema 演進要小心：不能隨便改型別，否則破壞 client。

MOOVO 場景判斷

建議：REST 為主，必要時加 BFF

  • B2B 後台（資料表單純）→ REST 夠用。
  • B2C 個人化 dashboard → GraphQL 有優勢但對這規模算 overkill。
面試這樣答

30 秒版本

「需求多變、要省流量、要聚合多來源 → GraphQL；公開 API、要 HTTP cache、檔案串流 → REST。MOOVO 我會選 REST 為主，因為資料模型還算單純，GraphQL 的 N+1 與 cache 複雜度不划算；真的需要前端聚合再加一層 BFF。」
