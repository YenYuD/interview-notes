DEMO 02 — 核心（這頁的主角）

5 條 queue，看 Event Loop 怎麼選下一個

面試最愛問「猜這段輸出順序」。其實它不是隨機 —— 每種非同步工作被丟進不同的 queue，Event Loop 照固定優先順序把它們撈出來執行。

記住一句：每做完一塊工作，先把 nextTick 和 microtask 清乾淨，才換下一個階段。
機制 — 巡邏路線

Event Loop 的六個階段

剛剛「進入階段輪巡」是什麼意思？Event Loop 每一圈會依序經過這六站，每站處理一種 callback：

1

Timers

執行到期的 setTimeout / setInterval callback。

2

Pending callbacks

延後到下一圈的系統 callback（如某些 TCP 錯誤）。

3

Idle / Prepare

Node 內部使用，跟我們無關。

4

Poll（最主要的工作站）

取得新的 I/O 事件、執行 I/O callback（讀檔、DB、網路回來的結果都在這收尾）。沒事做時會在這「等一下」。

5

Check

執行 setImmediate 的 callback。

6

Close callbacks

收尾用，如 socket.on('close', …)。

重點不是背滿六站，而是記住主角是 Poll（I/O），加上前面的 Timers、後面的 Check。而且 —— 每兩站之間都會插播一次「清空 nextTick + microtask」。
速查 — 誰先誰後

背這四層優先順序

面試被問「nextTick 跟 Promise.then 誰先？」直接答這張表：

0
同步程式碼整段 script 先一路跑到底，才輪到任何非同步
1
process.nextTick自己一條獨立 queue，優先於所有 microtask
2
microtaskPromise.then / catch / finally、queueMicrotask
3
macrotask（階段）Timers 的 setTimeout、Check 的 setImmediate、I/O callback
陷阱題：top-level 的 setTimeout(fn,0) 和 setImmediate 誰先？不一定（看程序啟動耗時）。但若兩者都寫在某個 I/O callback 裡，setImmediate 一定先 —— 因為 I/O 在 Poll 階段，下一站就是 Check。
DEMO 03 — 親眼看它卡死

為什麼「不要在主執行緒做重運算」

單執行緒的代價：只要有一塊同步程式碼跑很久，整條 Event Loop 就停擺 —— 計時器延遲、新請求進不來、畫面凍住。下面這顆轉圈圈代表「Event Loop 還活著」。

計時器每 10ms 應該要跳一次
同步那顆：轉圈圈完全凍住、計時器跳針 —— 因為 busy loop 霸佔了唯一的執行緒。
解法：CPU 密集（影像、加解密、大量計算）丟給 Worker Threads，或把工作切片用 setImmediate 分批做，讓 Event Loop 有空檔喘息。
別搞混

三個最常見的雷

✕

把 CPU 密集運算放主執行緒。 整個 server 卡住、所有請求一起變慢。重活丟 Worker Threads，或切片讓出執行緒。

✕

無限遞迴呼叫 process.nextTick。 nextTick 優先級最高，遞迴它會讓 microtask 和所有階段「餓死」，後面的 I/O 永遠輪不到。要遞迴改用 setImmediate。

✕

以為 setTimeout(fn, 0) 真的是 0ms。 它只是「下一輪 Timers 階段、且至少 0ms 後」才執行，前面排隊的同步、nextTick、microtask 都得先清完。

FINAL — 面試直接背這段

30 秒講完 Event Loop

「Node 用單一 JS 執行緒跑程式，耗時 I/O 交給底層 libuv 在背景做。Event Loop 輪巡六個階段（timers → pending → poll → check → close），主角是 Poll 收 I/O。重點在優先順序：同步先跑完，接著 process.nextTick，再來 microtask（Promise），最後才換下一個階段的 macrotask。所以它擅長 I/O 密集、不擅長 CPU 密集 —— 重運算會卡死整條執行緒，要丟給 Worker Threads。」
