API 設計

同一件事做很多次
結果只算一次

冪等性：同一個請求做 N 次跟做 1 次，對系統狀態的結果一樣。重點是「狀態一樣」，不是「回應一樣」。

DEMO 01 — 直覺

電梯按鈕：按 1 次跟按 50 次一樣

你進電梯狂按關門鍵，門不會因為你按得多就關得多。下面這顆隨便按，永遠只來一台電梯：

親手試試
你按了 0 次
來了 0 台電梯
關鍵：冪等的重點是「系統最後的狀態」一樣，不是每次的回應一樣。

弱網下你連點「付款」，會被扣幾次？

手機訊號爛，你按了付款轉圈圈沒回應，急了又按幾下 —— 每按一下 App 都偷偷送了一次請求。切換兩種伺服器，用力連點付款：

切換伺服器，然後狂點
你的餘額
$1,000
每次扣款 $100
模式：沒做冪等 — 點幾下扣幾次
// 伺服器收到的請求會顯示在這…
沒冪等：5 次點擊 = 扣 5 次。有 Idempotency-Key：後面 4 次伺服器一看「這把 key 處理過了」，直接回上次結果、不再扣款。
機制 — Stripe 的做法

Idempotency-Key 四步驟

1

Client 產生一把唯一的 key

通常是 UUID，放進 Idempotency-Key header。同一筆操作的 retry 用同一把。

2

Server 先查這把 key 看過沒

查 Redis / DB，順便比對 request body 的 hash，防止用同把 key 偷改金額。

3

沒看過 → 執行，然後存起來

存 key + 結果 + status code，設 TTL（例如 24 小時）。

✓

看過了 → 不重做，直接回上次結果

重送幾次都安全，因為實際只執行了一次。

速查

HTTP method 的冪等性

GET只讀
PUT覆蓋成同一份
DELETE刪到不存在為止
HEAD / OPTIONS只讀
POST每次新增一筆
PATCH看 body 寫法
陷阱題：DELETE 第二次回什麼？ 第一次 204、第二次 404。回應不一樣，但「那筆資料不存在」這個狀態一樣 —— 所以 DELETE 還是冪等的。
延伸追問 & 踩雷

別搞混

第一次還在處理，第二次同 key 進來？

回 409 Conflict 或讓它等（看設計）。

✕

把冪等跟快取搞混：快取是「相同 GET 回相同結果」；冪等是「相同寫入只生效一次」。

✕

只比對 key、沒比對 request body hash → client 拿同把 key 偷改金額會出包。

面試這樣答

30 秒版本

「冪等性是同一請求做幾次，對系統狀態的結果都一樣，重點在狀態、不在回應。金流一定要做，因為網路抖動會 retry。實作上讓 client 帶 Idempotency-Key，server 用 Redis 記這把 key 對應的結果，命中就直接回上次結果、TTL 設 24 小時，並存 request body 的 hash 防止同 key 改金額。」
